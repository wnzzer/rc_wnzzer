# notifyd —— 外部通知可靠投递服务

企业内部多个业务系统在关键事件发生时需要调用外部供应商的 HTTP(S) API。
**notifyd 把这件事从业务主链路上摘下来**：业务系统提交一个已构造完整的 HTTP 请求描述，
notifyd 持久化后立即返回；此后由它负责反复投递，直到成功或放弃。

**零第三方依赖**（只用 Go 标准库，`go.sum` 不存在），单静态二进制，单进程常驻。

```bash
make check   # gofmt + go vet + 脱敏检查 + 全部测试
make run     # 本地起一个实例
```

## 1. 我对这个问题的理解

需求给的是三个并列场景（广告回传 / CRM 状态变更 / 库存变更），但它们共享同一个
结构性问题：

> **一次关键业务事件的提交成功，被绑定在了一个不受控的第三方的可用性上。**

不做处理时业务代码会长成这样：注册成功 → 同步调广告商 API → 超时 5s →
用户注册接口 RT 飙到 5s，或者干脆失败回滚。**这是把别人的 SLA 写进了自己的 SLA。**

而需求里「业务系统不需要关心外部 API 的返回值」这句话，是整个设计**最关键的输入** ——
它意味着投递可以完全异步，也一次性排除了回调、结果队列、响应透传等一整类设计。

### 核心承诺只有两条

| | 承诺 | 含义 |
|---|---|---|
| **C1** | **收下就不丢** | 一旦返回 `202`，任务已 fsync 落盘。`kill -9`、掉电，重启后仍在。 |
| **C2** | **不放弃得太早** | 外部系统从抖动（分钟级）到宕机（小时级）都由 notifyd 吸收，业务方无感。 |

**C1 是硬承诺，任何性能优化都不能以牺牲它为代价。**
C2 是尽力而为，有明确的放弃条件，放弃时留下可人工干预的死信。

## 2. 整体架构

```
  业务系统 A ─┐
  业务系统 B ─┼─(1) POST /v1/notifications ──► ┌──────────────────────────────┐
  业务系统 C ─┘     签名 + 幂等键              │           notifyd            │
                                               │  ┌────────────────────────┐  │
                    ◄─(2) 202 Accepted ────────┤  │  Ingest  鉴权/校验/去重 │  │
                        (已 fsync 落盘)        │  └───────────┬────────────┘  │
                                               │      ┌───────▼────────┐      │
                                               │      │  WAL  journal  │◄─────┼── 启动时重放
                                               │      │  (append-only) │      │
                                               │      └───────┬────────┘      │
                                               │      ┌───────▼────────┐      │
                                               │      │  内存状态       │      │
                                               │      │  tasks / idem  │      │
                                               │      │  due min-heap  │      │
                                               │      └───────┬────────┘      │
                                               │      ┌───────▼────────┐      │
                                               │      │  Dispatcher     │      │
                                               │      │  worker pool    │      │
                                               │      │  per-host 限流   │      │
                                               │      └───────┬────────┘      │
                                               └──────────────┼───────────────┘
                                    ┌─────────────────────────┼──────────────┐
                                    ▼                         ▼              ▼
                              广告系统 API              CRM API         库存系统 API
```

三个组件，一个进程，一个磁盘文件。**刻意做到没有可拆分的部件** ——
v1 的复杂度预算全部花在「崩溃不丢」和「退避正确」上，不花在拓扑上。

```
cmd/notifyd/          入口、配置装配、有序退出
internal/model/       任务与状态定义、ID 生成
internal/store/       Store 接口 + append-only WAL 实现
internal/queue/       内存状态：幂等索引、到期最小堆、保留期清理、压缩
internal/dispatch/    退避、失败分类、SSRF 客户端、worker 池
internal/api/         HTTP 接口 + HMAC 签名鉴权
internal/metrics/     手写 Prometheus 文本格式
test/acceptance/      A1-A10 验收测试（启动真实进程 + kill -9）
```

## 3. 关键工程决策与取舍

> 完整的 47 条决策记录（其中 **15 条状态为「已否决」或「暂缓」**，另有 4 条采纳项内部记录了被否决的备选）见 [`docs/decisions.md`](docs/decisions.md)。
> 这里只列最核心的五条。

### 3.1 投递语义：at-least-once，并写进对外契约

一次 POST 超时后，「对方没收到」和「对方收到了但响应丢了」这两种世界状态
在本服务侧**不可区分**。任何号称 exactly-once 的实现，要么依赖对端配合，要么在撒谎。

因此诚实的做法是选 at-least-once，把重复的可能性**明确暴露**出去。
同时区分两种幂等，责任划清楚：

| | 入口幂等（去重**提交**） | 出口幂等（去重**投递**） |
|---|---|---|
| 谁负责 | **notifyd**，强保证 | **供应商**，notifyd 只能协助 |
| 机制 | `idempotency_key` 必填，命中直接返回已有任务 | 每次投递携带**恒定不变**的 `X-Notify-Id` |

这一对概念的混淆，是这类系统最常见的设计事故。

### 3.2 非对称 fsync：把持久化成本花在唯一需要它的地方

对四类 WAL 记录分别追问「丢了会怎样」，答案是非对称的：

| 记录 | 丢失后果 | 违反 C1？ | 策略 |
|---|---|---|---|
| `enq` | **任务彻底消失**，且无人知晓 | **是** | **同步 fsync**，返回 202 前完成 |
| `att` | 重试次数偏小，多试几次 | 否 | 不 fsync |
| `ok` | 已成功的任务被重投一次 | 否 | 不 fsync |
| `dead` | 死信回队，再走一遍 | 否 | 不 fsync |

**除了 `enq`，其余记录的丢失后果都已被 at-least-once 语义本身吸收。**
而 `ok` 恰好是数量上最多的记录，对它 fsync 会让吞吐掉一个数量级却换不到任何正确性。

代价写清楚：崩溃时最近 200ms 内成功投递的任务可能被重投一次 ——
这是**主动选择的重复**，落在契约内。

### 3.3 退避参数是算出来的，不是拍的

```
base = 1s,  cap = 1h,  max_attempts = 24
window_n = min(cap, base * 2^(n-1))
delay_n  = random_uniform(0, window_n)     ← full jitter
```

| max_attempts | 最坏覆盖 | 期望覆盖 |
|---|---|---|
| 12 | 0.6h | 0.3h |
| **24** | **12.1h** | **6.1h** |

初稿写的是 12 —— 只覆盖期望 18 分钟，且 `cap=1h` 在该次数下**从未被触发**，
与承诺 C2 的「小时级宕机」直接矛盾。这是交付前把参数**算了一遍**才发现的
（见 [AI_USAGE.md §4.1](AI_USAGE.md)）。

**为什么用 full jitter 而非固定指数**：供应商宕机 10 分钟、积压 5000 任务时，
确定性退避会让这 5000 次重试聚集在同一秒 —— 对端刚恢复就被二次打垮。
full jitter 把重试时刻均匀铺开，是三种做法中对端压力峰值最低的一种。
代价是单任务期望延迟翻倍 —— 我们优化的是**对端的存活概率**，不是单条通知的 P50。

### 3.4 重试前先问「重试有意义吗」

盲目重试所有失败是这类系统最常见的实现缺陷。

| 对端结果 | 判定 |
|---|---|
| `2xx` | 成功 |
| `408` `429` `5xx` / 网络错误 / 超时 | 可重试（`429` 优先采用 `Retry-After`，封顶） |
| **其余 `4xx`** | **永久失败，不重试** |
| `3xx` | **永久失败，不跟随重定向** |

`401/403` 归为永久失败尤其重要：凭据错误重试 24 次不会变对，
只会在对端积累一串认证失败记录，可能触发账号锁定。
不跟随 `3xx` 则是因为跟随会让 SSRF 校验被一个 302 绕过 —— **安全性优先于便利性**。

### 3.5 用开源中间件吗？不用，以及不用时的替代方案

作业要求说明用/不用中间件的理由。检验方法是**逐条对照 MQ 的核心能力**：

| MQ 提供什么 | 本需求用得上吗 |
|---|---|
| 分区有序 | ❌ 三个业务场景没有一个需要顺序 |
| 消费者组水平扩展 | ❌ 单实例足够 |
| 日志重放 | ❌ 不需要重放历史流量 |
| 跨系统解耦 | ❌ 解耦本来就是本服务自身提供的 |

**一条都用不上。** 引入它等于把「一个本地文件的复杂度」换成「一个集群的复杂度」。

**替代方案**：本地 append-only WAL。在单机可承载的量级下，它提供了 MQ 在本场景中
被实际用到的全部能力。**什么时候改变主意**：见 §6 演进 Stage 4。

## 4. 系统边界

### 解决

异步解耦 · 持久化排队 · 指数退避重试 · 失败分类 · 入口幂等 ·
对称密钥签名鉴权 · SSRF 防护 · 死信与人工重投 · 可观测性

### 明确**不**解决

> 这一节被刻意写得比上一节更详细 —— **边界是靠说清楚不做什么来定义的。**
> 完整 10 条见 [spec §2.2](docs/spec.md)。

| 不做 | 理由 | 谁负责 |
|---|---|---|
| **精确一次投递** | 跨越不受控的 HTTP 边界，超时时无法区分「没收到」与「收到了但响应丢了」 | 供应商按 `X-Notify-Id` 去重 |
| **投递顺序保证** | 有重试必有乱序；保序要串行 + 队头阻塞，而三个业务场景没一个需要 | 业务方合并通知 |
| **响应内容处理 / 回调** | 需求原文：业务系统不关心返回值。做回调等于把刚解开的耦合重新系上 | —— |
| **供应商协议适配**（token 刷新、签名、字段映射） | **无界**需求，最终长成适配器地狱；且只有业务系统知道该往 CRM 传什么 | 业务系统构造完整请求 |
| **多实例 HA** | 单写者正确性易自证；分布式抢占/脑裂是这类系统事故的主要来源 | 见演进 Stage 2 |
| **多租户配额、定时通知、优先级队列** | 需求中不存在 | 有需求再说 |

### 已知限制（自曝清单）

不藏在角落，[spec §11](docs/spec.md) 集中列了 10 条。最需要知道的三条：

1. **单点** —— 进程宕机期间无法接收新通知（已接收的不丢）。
2. **幂等窗口 = 成功任务保留期（默认 7 天）** —— 超窗重投会产生新任务。死信独立保留 30 天。
3. **只鉴权、未授权** —— 任意持有有效密钥的调用方可读取/重投他人任务（凭据不泄露）。
   已知且**有意暂缓**（[D-046](docs/decisions.md#d-046)）。
4. **明文 HTTP** —— 签名保完整性**不保机密性**，假设部署在受信内网（[D-047](docs/decisions.md#d-047)）。
5. **`200` 包裹业务错误判为成功** —— 判定不改（保持"字节忠实管道"定位），
   但响应摘要已保留以便排查。
6. **磁盘无总量上限** —— 内存有 `NOTIFY_TASKS_MAX` 兜底，磁盘只靠保留期与压缩控制。

## 5. 接口

```bash
POST   /v1/notifications            提交通知 → 202（已落盘）/ 200（幂等命中）
GET    /v1/notifications/{id}       查状态与尝试历史（排障用，不供业务逻辑依赖）
GET    /v1/notifications?state=dead 死信列表
POST   /v1/notifications/{id}/retry 手工重投死信 ← 「供应商宕机三天」的运维出口
GET    /healthz                     存活探针（无外部依赖，不会因别人故障而误报）
GET    /metrics                     Prometheus 文本格式（手写，零依赖）
```

**鉴权**：HMAC-SHA256 签名，签名串覆盖 **body 的哈希**而非只有时间戳 ——
因为请求体里装着**目标 URL**，只签时间戳的话中间人能把投递目的地改成自己的服务器。

完整请求/响应格式见 [spec §4](docs/spec.md)，可直接运行的签名示例见
[`scripts/notify-submit.sh`](scripts/notify-submit.sh)（该脚本本身被验收测试覆盖）。

**最值得告警的指标**是 `notifyd_oldest_pending_age_seconds` ——
它单独一条就能回答「是不是有东西卡住了」。队列深度正常但最老任务年龄持续上涨，
说明存在一个投不出去的目标在反复退避。

## 6. 演进路线

演进的前提是**先有触发信号**，而不是先有计划。每阶段写明「什么信号出现时才做」。

| 阶段 | 触发信号 | 做什么 |
|---|---|---|
| **1（当前）** | —— | 单实例 + 本地 WAL，垂直扩展 |
| **2** | 单点不可接受，或单机磁盘/吞吐见顶 | `Store` 接口换 PostgreSQL，`FOR UPDATE SKIP LOCKED` 天然提供多实例抢占；notifyd 变无状态 |
| **3** | 单个供应商故障开始影响其他供应商 | 按目标 host 分区队列 + 独立 worker 池；此时熔断器的收益才超过其复杂度 |
| **4** | 出现顺序性需求、跨区域部署、或需重放历史流量 | 引入 Kafka —— 到这时分区有序 / 消费者组 / 日志重放三样全都用得上，它才配得上运维成本 |

`Store` 接口是**全项目唯一一处为未来留的口子**。允许它存在的条件有两个且缺一不可：
(1) 几乎零成本（本来就要分层）；(2) 不留的代价很高（文件 IO 会渗透进调度逻辑）。
判断越界的标准：**一个抽象若需要「注册机制 / 配置驱动的实现选择 / 生命周期钩子」，
它就越界了。**

## 7. 测试

```bash
make test        # 单元测试 + 验收测试
make test-race   # 竞态检测（会用 -race 重新构建被测二进制）
```

验收测试 **A1-A10 全部实现并通过**，它们启动**真实的 notifyd 进程**并发起真实 HTTP 请求：

| # | 场景 | 断言 |
|---|---|---|
| A1 | 返回 202 后立即 `kill -9` | 重启后任务仍在，最终被投递 |
| A2 | 目标持续 `503` | 重试间隔呈增长趋势；达上限后进死信 |
| A3 | 目标返回 `400` | **一次**尝试后进死信，不重试 |
| A4 | 同幂等键并发提交 100 次 | 只产生 1 个任务 |
| A5 | 目标指向回环 / 云 metadata / CGNAT / IPv4-mapped IPv6 | 全部被拒 |
| A6 | 签名篡改 / 未知 key / 时间戳偏移 10 分钟 | `401` |
| A7 | 一个目标 host 恒定挂起 3s | 其他 host 的投递不受影响 |
| A8 | 60 个任务同时失败 | 重试时刻被 jitter 打散，不形成尖峰 |
| A9 | 532 次重试 + 压缩 | journal 稳定在 17KB；重启后状态与幂等去重均一致 |
| A10 | 队列达上限 | 新提交 `429`，已有任务不受影响 |

补充用例：签名覆盖 body（篡改目标 URL 必须 401）、`X-Notify-Id` 跨重试恒定、
死信查询与重投、示例客户端脚本可用。

**关于 `-race`**：验收测试启动的是独立进程，只给测试二进制开 `-race` 检测不到
notifyd 内部的并发（32 worker + 共享队列 + 后台刷盘）。因此用 `//go:build race`
让 race 模式下给被测二进制也加上 `-race`。
一个跑了 `-race` 却没覆盖主体代码的测试，给的是虚假的安全感。
