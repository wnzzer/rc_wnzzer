# notifyd —— 外部通知可靠投递服务

> 企业内部多个业务系统在关键事件发生时需要调用外部供应商的 HTTP(S) API。
> **notifyd 把这件事从业务主链路上摘下来**：业务系统提交一个已构造完整的 HTTP
> 请求描述，notifyd 持久化后立即返回；此后由它负责反复投递，直到成功或放弃。

## 一、我对这个问题的理解

> **对应交付物 1-①**

需求给了三个并列场景（广告回传 / CRM 状态变更 / 库存变更），但它们共享同一个结构性问题：

> **一次关键业务事件的提交成功，被绑定在了一个不受控的第三方的可用性上。**

不做处理时业务代码会长成这样：

```
用户注册成功 → 同步调广告商 API → 超时 5s → 注册接口 RT 飙到 5s，或者干脆失败回滚
```

**这是把别人的 SLA 写进了自己的 SLA。**

而需求里「业务系统**不需要关心**外部 API 的返回值」这句话，是整个设计**最关键的输入** ——
它意味着投递可以完全异步，也**一次性排除**了回调、结果队列、响应透传等一整类设计。

### 核心承诺只有两条

| | 承诺 | 含义 |
|:-:|---|---|
| **C1** | **收下就不丢** | 一旦返回 `202`，任务已 fsync 落盘。`kill -9`、掉电，重启后仍在。 |
| **C2** | **不放弃得太早** | 外部系统从抖动（分钟级）到宕机（小时级）都由 notifyd 吸收，业务方无感。 |

> **C1 是硬承诺**，任何性能优化都不能以牺牲它为代价。
> **C2 是尽力而为**，有明确的放弃条件，放弃时留下可人工干预的死信。

### 一个必须说清楚的前提

「稳定、可靠地送达」在分布式语境下**只能**落到 at-least-once。
把「不重复」的责任错误地放在本系统，是这类系统最常见的设计事故 —— 详见 [§4.1](#41-投递语义at-least-once)。

## 二、整体架构与核心设计

> **对应交付物 1-②**

### 2.1 数据流

```
  业务系统 A ─┐
  业务系统 B ─┼─(1) POST /v1/notifications ──► ┌──────────────────────────────┐
  业务系统 C ─┘     签名 + 幂等键              │           notifyd            │
                                               │  ┌────────────────────────┐  │
                    ◄─(2) 202 Accepted ────────┤  │  Ingest  鉴权/校验/去重 │  │
                        (已 fsync 落盘)        │  └───────────┬────────────┘  │
                                               │      ┌───────▼────────┐      │
                                               │      │  WAL  journal  │◄─────┼── 启动时重放
                                               │      │  (append-only) │      │
                                               │      └───────┬────────┘      │
                                               │      ┌───────▼────────┐      │
                                               │      │  内存状态       │      │
                                               │      │  tasks / idem  │      │
                                               │      │  due min-heap  │      │
                                               │      └───────┬────────┘      │
                                               │      ┌───────▼────────┐      │
                                               │      │  Dispatcher     │      │
                                               │      │  worker pool    │      │
                                               │      │  per-host 限流   │      │
                                               │      └───────┬────────┘      │
                                               └──────────────┼───────────────┘
                                    ┌─────────────────────────┼──────────────┐
                                    ▼                         ▼              ▼
                              广告系统 API              CRM API         库存系统 API
```

**三个组件，一个进程，一个磁盘文件 —— 刻意做到没有可拆分的部件。**
v1 的复杂度预算全部花在「崩溃不丢」和「退避正确」上，不花在拓扑上。

### 2.2 任务状态机

```
                  ┌─────────┐
   POST ─fsync──► │ pending │
                  └────┬────┘
                       │ 到期出队
                  ┌────▼────┐
        ┌─────────│ sending │─────────┐
        │ 2xx     └────┬────┘   永久失败/超限
        │              │ 可重试失败      │
   ┌────▼──────┐  ┌────▼────┐     ┌────▼───┐
   │ succeeded │  │ waiting │     │  dead  │
   └───────────┘  └────┬────┘     └────┬───┘
                       │ 退避到期        │ POST /retry
                       └────► pending ◄─┘
```

崩溃时停留在 `sending` 的任务，重放后回到 `pending` —— 详见 [§4.3](#43-崩溃与恢复)。

### 2.3 代码结构

```
cmd/notifyd/          入口、配置装配、有序退出
internal/
  model/              任务与状态定义、ID 生成
  store/              Store 接口 + append-only WAL 实现   ← 技术难度最高的部分
  queue/              内存状态：幂等索引、到期最小堆、保留期清理、压缩
  dispatch/           退避、失败分类、SSRF 客户端、worker 池
  api/                HTTP 接口 + HMAC 签名鉴权
  metrics/            手写 Prometheus 文本格式
  testutil/           可编程的接收端模拟器（仅测试引用，不进生产二进制）
test/acceptance/      A1-A10 验收测试（启动真实进程 + kill -9）
```

## 三、系统边界【必答题 1】

> **对应设计说明要求 1**：哪些问题选择在这个系统中解决？哪些明确选择不解决？为什么？

### 3.1 选择解决的

| 问题 | 机制 |
|---|---|
| 异步解耦 | 落盘即返回 `202`，业务主链路不等待第三方 |
| 持久化排队 | append-only WAL，进程崩溃/掉电不丢 |
| 重试与退避 | 指数退避 + full jitter，吸收对端抖动与短期不可用 |
| 失败分类 | 区分「重试有意义」与「重试只是浪费」，后者立即终止 |
| 入口幂等 | `idempotency_key` 必填，重复提交只产生一个任务 |
| 鉴权与完整性 | HMAC-SHA256 签名，覆盖 body 哈希 |
| SSRF 防护 | Dial 层校验真实 IP + 禁止跟随重定向 |
| 死信与人工干预 | 放弃的任务可查询、可手工重投 |
| 可观测 | 任务状态可查、7 项 Prometheus 指标 |

### 3.2 明确**不**解决的

> 这一节被刻意写得比上一节更详细 —— **边界是靠说清楚不做什么来定义的。**

| # | 不做 | 理由 | 谁负责 |
|:-:|---|---|---|
| **B1** | **精确一次投递** | 跨越不受控的 HTTP 边界，超时时**根本无法区分**「对方没收到」与「对方收到了但响应丢了」。任何号称 exactly-once 的实现，要么依赖对端配合，要么在撒谎。 | 供应商按 `X-Notify-Id` 去重 |
| **B2** | **投递顺序保证** | 有重试就必然有乱序；保序要串行 + 队头阻塞，一个慢任务卡死整条队列。而三个业务场景**没有一个**需要顺序。 | 业务方合并为单次通知 |
| **B3** | **响应内容处理 / 回调业务方** | 需求原文：业务系统不关心返回值。做回调等于**凭空重建一条同步链路**，把刚解开的耦合重新系上（回调失败了又该怎么重试？递归了）。 | —— |
| **B4** | **供应商协议适配**（token 刷新、签名算法、payload 模板） | **无界**需求：每接一家就改一次 notifyd，最终长成谁也不敢动的适配器地狱，发布节奏被最慢的供应商绑架。更根本的是：**只有业务系统知道该往 CRM 传什么状态**。 | 业务系统构造完整请求 |
| **B5** | **多实例 HA / 水平扩展** | 单写者日志的正确性容易自证；多实例要处理任务抢占、租约续期、脑裂下的重复投递、时钟漂移 —— 这正是这类系统绝大多数事故的来源。 | 见 [§6.2 Stage 2](#62-演进路线) |
| **B6** | **定时/延时通知、优先级队列、按供应商限速** | 需求中不存在。加进来会让调度器从「一个最小堆」变成「多队列 + 令牌桶 + 优先级抢占」。 | 有需求再加 |
| **B7** | **多租户配额** | 调用方是内部系统，同一信任域。v1 用「一个业务系统一个 key」做审计归属。 | 内网信任边界 |
| **B8** | **超过保留期的幂等去重** | 去重表常驻内存，不能无限增长。去重窗口 = 成功任务保留期（默认 7 天）。 | 已写入 API 文档 |
| **B9** | **传输内容的静态加密 / KMS** | 任务体本来就要明文发给第三方，磁盘加密属基础设施层职责。应用层再加一层是**安全剧场** —— 看起来更安全，实际多了密钥管理这个新失败点。 | 运维层 |
| **B10** | **死信管理 Web UI** | 一个 HTTP 接口 + curl 足够覆盖 v1 的运维需求。 | 见 [§6.2](#62-演进路线) |

### 3.3 已知限制（自曝清单）

> 不藏在角落。完整 13 条见 [spec §11](docs/spec.md)，这里列最该知道的六条。

| 限制 | 性质 |
|---|---|
| **单点** —— 进程宕机期间无法接收新通知（已接收的不丢） | 明确取舍（B5） |
| **幂等窗口 = 成功任务保留期（7 天）**，死信独立保留 30 天 | 明确取舍（B8） |

## 四、可靠性与失败处理【必答题 2】

> **对应设计说明要求 2**：投递语义是什么？外部系统失败或长期不可用时的策略是什么？

### 4.1 投递语义：at-least-once

**选择 at-least-once，并把「可能重复」作为对外的显式契约写进 API 文档。**

不选 **at-most-once**：会丢通知，与承诺 C1 直接冲突。

不选 **exactly-once**：做不到。当一次 POST 超时，notifyd 面对两种可能的世界状态：

```
① 请求没到达对端        → 不重试就丢了
② 请求到达并被处理，响应在回程丢了 → 重试就重复了
```

**这两种状态在 notifyd 这一侧无法区分**，没有任何本地机制能消除这个歧义。
唯一的出路是让对端去重，而对端是否去重不由我们决定。
因此诚实的做法是：选 at-least-once，把重复的可能性**明确暴露**出去。

### 4.2 两种幂等，责任在不同的人

> 这一对概念的混淆，是这类系统最常见的设计事故。

| | **入口幂等**（去重*提交*） | **出口幂等**（去重*投递*） |
|---|---|---|
| 问题 | 业务系统重试提交，产生多个任务 | notifyd 重试投递，供应商收到多次 |
| 谁负责 | **notifyd 负责**，强保证 | **供应商负责**，notifyd 只能协助 |
| 机制 | `idempotency_key` 必填，命中索引直接返回已有任务 | 每次投递携带**恒定不变**的 `X-Notify-Id`，`X-Notify-Attempt` 递增 |
| 边界 | 去重窗口 = 保留期（B8） | 供应商若不去重，重复就会发生（B1） |

### 4.3 崩溃与恢复

**非对称 fsync —— 把持久化成本精确花在唯一需要它的地方。**

对四类 WAL 记录分别追问「丢了会怎样」，答案是非对称的：

| 记录 | 丢失后果 | 违反 C1？ | 策略 |
|---|---|:-:|---|
| `enq` | **任务彻底消失**，业务方以为发了、实际没发，且无人知晓 | **是** | **同步 fsync**，返回 202 前完成 |
| `att` | 重试次数偏小，多试几次 | 否 | 不 fsync |
| `ok` | 已成功的任务被重投一次 | 否 | 不 fsync |
| `dead` | 死信回队，再走一遍失败流程 | 否 | 不 fsync |

> **除了 `enq`，其余记录的丢失后果都已被 at-least-once 语义本身吸收。**
> 而 `ok` 恰好是数量上**最多**的记录 —— 对它 fsync 会让吞吐掉一个数量级，
> 却换不到任何正确性。

代价写清楚：崩溃时最近 200ms 内成功投递的任务可能被重投一次。
这是**主动选择的重复**，落在契约内。

**恢复语义**：崩溃时处于 `sending` 的任务无法知道是否已送达，一律**重新投递** ——
我们选择「可能重复」而不是「可能丢失」，因为 C1 优先级更高。

**尾部截断修复**：append-only + 单写者下，崩溃唯一可能造成的损坏是尾部半截写入。
逐行解析，遇到无法解析的行就截断到最后一个完好偏移。
**不处理**中段位翻转 —— 那是文件系统与硬件的职责（[D-007](docs/decisions.md#d-007)）。

### 4.4 外部系统失败：先问「重试有意义吗」

> 盲目重试所有失败是这类系统最常见的实现缺陷。

| 对端结果 | 判定 | 动作 |
|---|:-:|---|
| `2xx` | ✅ 成功 | → `succeeded` |
| `408` `429` | 🔄 可重试 | 退避；`429` 优先采用 `Retry-After`（封顶 1h） |
| `5xx` | 🔄 可重试 | 退避 |
| 连接被拒 / DNS 失败 / TLS 失败 / 超时 | 🔄 可重试 | 退避 |
| **其余 `4xx`**（400/401/403/404/422…） | ❌ 永久失败 | **不重试**，直接 → `dead` |
| `3xx` | ❌ 永久失败 | **不跟随重定向**，见下 |
| 目标命中 SSRF 黑名单 | ❌ 永久失败 | → `dead`，原因 `blocked_target` |

**`401/403` 归为永久失败尤其重要**：凭据错误重试 24 次不会变对，
只会在对端积累一串认证失败记录，可能**触发账号锁定**。正确处理是立即进死信 + 告警。

**不跟随 `3xx`**：Go 的 `http.Client` 默认跟随，而跟随会让 SSRF 校验被一个
`302 Location: http://169.254.169.254/` 绕过。**安全性优先于便利性**。

### 4.5 外部系统长期不可用：退避 + 隔离 + 死信

**① 指数退避 + full jitter**

```
base = 1s,  cap = 1h,  max_attempts = 24

window_n = min(cap, base × 2^(n-1))
delay_n  = random_uniform(0, window_n)     ← full jitter
```

参数是**算出来的**，不是拍的：

| max_attempts | 最坏覆盖 | 期望覆盖 |
|:-:|:-:|:-:|
| 12 | 0.6h | 0.3h |
| **24** | **12.1h** | **6.1h** |

> 初稿写的是 12 —— 只覆盖期望 18 分钟，且 `cap=1h` 在该次数下**从未被触发**，
> 与 C2 的「小时级宕机」直接矛盾。这是交付前把参数**算了一遍**才发现的，
> 详见 [AI_USAGE 附录 A.1](AI_USAGE.md#a1-spec-里的默认参数自相矛盾交付前自查发现)。

**为什么用 full jitter 而非固定指数**：供应商宕机 10 分钟、积压 5000 任务时，
确定性退避会让这 5000 次重试聚集在同一秒 —— **对端刚恢复就被二次打垮**，
形成「恢复 → 再崩 → 再积压」的循环。full jitter 把重试时刻均匀铺开，
是三种做法中对端压力峰值最低的一种。
代价是单任务期望延迟翻倍 —— 我们优化的是**对端的存活概率**，不是单条通知的 P50。

**② per-host 并发隔离**

没有它，一个 RT 30s 的供应商会占满全部 32 个 worker，**其余所有供应商的通知一起饿死**。
这是这类系统最典型的生产事故，而修复成本只有约 20 行。

**③ 双重放弃条件 + 死信**

满足任一即终止：`attempts >= 24` ｜ `now >= created_at + 24h` ｜ 判定为永久失败。

死信**不删除**，保留 30 天（比成功记录的 7 天长 —— 它是通知未送达的**证据**），
可查询、可通过 `POST /{id}/retry` 手工重投。这是「供应商宕机三天」场景的运维出口。

**④ 背压**

活跃任务达 `NOTIFY_QUEUE_MAX` 后返回 `429` + `Retry-After`。
**早拒绝好过晚崩溃**：拒绝时调用方能自行降级；OOM 时调用方什么也拿不到，
而且承诺 C1 直接破产。

## 五、关键工程决策与取舍

> **对应交付物 1-③**。这里是五条最核心的；完整 **47 条决策（含 15 条否决/暂缓）** 见
> [`docs/decisions.md`](docs/decisions.md)，每条含背景、选项、代价与反悔成本。

### 5.1 零第三方依赖 + 单常驻进程

这个系统的真实复杂度**不在「接请求」也不在「发请求」**，而在
**崩溃不丢 + 退避正确 + 失败分类**。引入框架不会让这三件事变简单，只会把它们藏进
一堆配置里。反过来，零依赖**强迫每一行复杂度都被显式写出来、被显式论证**。

这条约束同时起到了防止过度设计的作用：任何「引入 X 就能解决」的建议，
在它面前都必须先回答「不引入时替代方案是什么、代价是什么」。

### 5.2 Go + 手写 WAL，而不是 Python + stdlib `sqlite3`

零依赖下这两者必须**联合选择**。三个方案，各自的代价都摆在明面上：

| 方案 | 优势 | 代价 |
|---|---|---|
| **A. Go + 手写 WAL** ✅ | 单静态二进制；最贴合「常驻后台服务」 | 约 300 行自研存储层，**正确性需自证** |
| B. Python + `sqlite3` | 仍算零依赖，白拿 WAL 模式的崩溃安全 | `http.server` 偏弱；部署要带运行时 |
| C. Go + 纯内存队列 | 代码量最小 | **重启丢全部在途任务**，与「可靠送达」正面冲突 |

C 违反 C1，出局。A vs B 是真正的权衡 —— B 用标准库换来免费的持久化正确性，
这是个强论点。选 A 是因为**非对称 fsync 策略、尾部截断修复、rename 原子压缩**
正是最能体现工程判断的部分，用 SQLite 会把这部分思考整个外包掉。

为此接受的代价是「正确性需自证」，这笔债在 [§八](#八测试与验证) 还掉了。

### 5.3 唯一为未来留的口子：`Store` 接口

MVP 原则要求拒绝一切推测性抽象。这是唯一的例外，因此需要单独论证 ——
**两个条件同时成立才允许留口子**：

1. **几乎零成本**：本来就要把存储和调度分层，定义接口不增加额外代码；
2. **不留的代价很高**：否则文件 IO 会渗透进调度逻辑，Stage 2 换存储等于重写。

**越界判据**：一个抽象若需要「注册机制 / 配置驱动的实现选择 / 生命周期钩子」，
它就越界了。`Store` 接口没有这些 —— 而 AI 建议的「可插拔存储插件框架」有，所以被否决。

### 5.4 对称密钥签名：为什么签的是 body 的哈希

```
canonical = "v1\nPOST\n/v1/notifications\n<timestamp>\n" + hex(sha256(raw_body))
```

**本服务的请求体里装着目标 URL。**
若只签时间戳，任何能改写请求体的中间人都能把一条「通知 CRM」改写成
「把用户数据 POST 到攻击者的服务器」—— 而签名依然有效。

**为什么没有 nonce 缓存**（一处刻意的**减法**）：`idempotency_key` 强制必填后，
重放一个完整请求在应用层天然是 no-op。
**时间戳窗口负责限制重放窗口，幂等键负责让重放无害，两者已经闭合。**
再维护一张带淘汰策略的 nonce 表，是用新的有状态组件解决已被解决的问题。

### 5.5 开源中间件：不用，以及不用时的替代方案

> **对应作业「其他说明」**：允许使用开源中间件；若使用需说明为什么选它、不使用时的替代方案。

**结论：不使用任何开源中间件。** 检验方法是**逐条对照 MQ 的核心能力**：

| MQ 提供什么 | 本需求用得上吗 |
|---|---|
| 分区有序 | ❌ 三个业务场景没有一个需要顺序（B2） |
| 消费者组水平扩展 | ❌ 单实例足够（B5） |
| 日志重放 | ❌ 不需要重放历史流量 |
| 跨系统解耦 | ❌ 解耦本来就是本服务自身提供的 |

**一条都用不上。** 引入它等于把「一个本地文件的复杂度」换成「一个集群的复杂度」：
运维、容量规划、版本升级、监控，外加一个新的 SPOF。

| 若不使用，替代方案是什么 | |
|---|---|
| MQ（Kafka/RabbitMQ/Redis） | 本地 append-only WAL（[spec §7](docs/spec.md)） |
| 外部数据库 + 调度框架（Quartz/XXL-JOB） | `container/heap` 最小堆 + 一个 timer |
| metrics SDK（client_golang/OTel） | 手写 Prometheus 文本格式，约 100 行 |
| 配置库（viper/yaml） | 环境变量，约 60 行 |
| Web 框架 / router | 标准库 `ServeMux` 的方法+路径模式（Go 1.22+） |

**什么时候会改变主意**：见 [§6.2 Stage 4](#62-演进路线) —— 到那时 MQ 的四项能力会同时用上。

## 六、取舍与演进【必答题 3】

> **对应设计说明要求 3**：哪些 AI 方案是「过度的」？未来流量或复杂度增长时如何演进？

### 6.1 哪些 AI 建议被判为「过度设计」

> 完整论证见 [`AI_USAGE.md` §二](AI_USAGE.md) 与 [`docs/decisions.md`](docs/decisions.md)。
> 判据只有一句：**不加它，v1 会坏在哪？** 答不上来就进否决区。

| AI 的建议 | 否决理由（一句话） | 重新引入时机 |
|---|---|---|
| **消息队列** Kafka/RabbitMQ/Redis | 四项核心能力一条都用不上 | Stage 4 |
| **熔断器** | 退避 + per-host 上限已覆盖其 80% 收益；阈值无先验数据可调，**误熔断比不熔断更危险** | Stage 3 |
| **供应商适配层 / 模板引擎** | **无界**需求，会长成适配器地狱；且适配逻辑属业务侧知识 | 抽共享客户端库，而非塞进中继服务 |
| **多实例 HA + 分布式锁** | 分布式抢占/脑裂是这类系统事故的主要来源 | Stage 2，用 DB 的 `SKIP LOCKED` 而非自研锁 |
| **外部 DB + 调度框架** | 为跑一个 timer 循环引入两套需独立运维的基础设施 | Stage 2 |
| **可插拔存储插件框架** | v1 只有一个实现，为一个实现建注册表是推测性通用化 | —— |
| **WAL 记录加 CRC** | 单写者 append-only 下唯一的损坏形态是尾部截断，已被覆盖；防位翻转是文件系统职责 | —— |
| **gRPC / protobuf** | 瓶颈在外部网络 IO 不在序列化；且给每个接入方增加成本 | —— |
| **metrics SDK** | 为暴露 7 个指标拖入一串传递依赖 | —— |
| **任务体静态加密 / KMS** | 数据本来就要明文发给第三方，是**安全剧场** | —— |
| **死信管理 Web UI** | 接口 + curl 足够；零依赖下还得手写前端 | 运维频次真的高起来时 |

**否决不是永久判决，是当前阶段的成本收益判断。**
所以每条都绑定了一个具体的**触发信号**，而不是一句「以后再说」。

### 6.2 演进路线

> 演进的前提是**先有触发信号**，而不是先有计划。

| 阶段 | 触发信号 | 做什么 |
|:-:|---|---|
| **1**<br>当前 | —— | 单实例 + 本地 WAL，垂直扩展。适用：日均百万级以内，可容忍分钟级维护窗口 |
| **2** | 单点不可接受，或单机磁盘/吞吐见顶 | `Store` 接口换 PostgreSQL，`FOR UPDATE SKIP LOCKED` **天然提供多实例抢占**；notifyd 变无状态，前面挂 LB |
| **3** | 单个供应商故障开始影响其他供应商 | 按目标 host 分区队列 + 独立 worker 池；**此时熔断器的收益才超过其复杂度**，可加按供应商限速 |
| **4** | 出现顺序性需求、跨区域部署、或需重放历史流量 | 引入 Kafka —— 到这时分区有序 / 消费者组 / 日志重放**三样全都用得上**，它才配得上运维成本 |

**其他增量**（按需，无固定顺序）：调用方级授权（[D-046](docs/decisions.md#d-046)）、
HTTPS（[D-047](docs/decisions.md#d-047)）、死信过期前自动导出与告警、
按调用方配额、磁盘总量上限。

## 七、接口

### 7.1 路由

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/v1/notifications` | 提交通知 → `202`（已落盘）/ `200`（幂等命中） |
| `GET` | `/v1/notifications/{id}` | 查状态与尝试历史（排障用，**不供业务逻辑依赖**） |
| `GET` | `/v1/notifications?state=dead` | 死信列表 |
| `POST` | `/v1/notifications/{id}/retry` | 手工重投死信 ← 「供应商宕机三天」的运维出口 |
| `GET` | `/healthz` | 存活探针（无外部依赖，不会因别人故障而误报） |
| `GET` | `/metrics` | Prometheus 文本格式（手写，零依赖） |

### 7.2 提交请求

```jsonc
{
  "idempotency_key": "order-98765-paid",      // 必填，≤128B
  "target": {
    "url": "https://vendor.example.com/hook", // 必填，仅 http/https
    "method": "POST",
    "headers": { "Authorization": "Bearer <vendor-token>" },
    "body": "{\"contact_id\":123,\"status\":\"paid\"}",
    "body_encoding": "utf8"                    // utf8 | base64
  },
  "policy": { "timeout_ms": 5000, "max_attempts": 24, "deadline_ms": 86400000 }
}
```

**`body` 为什么是字符串而不是 JSON 对象**：若由 notifyd 重新序列化，字段顺序与空白会变，
而**不少供应商对原始 payload 字节做签名校验** —— 重序列化会让签名失效，
且这个 bug 只在特定供应商上出现，排查时几乎不会往「中继服务改了我的 JSON」这个方向想。

鉴权头与签名算法见 [spec §4.1](docs/spec.md)，可直接运行的示例见
[`scripts/notify-submit.sh`](scripts/notify-submit.sh)（该脚本本身被验收测试覆盖）。

### 7.3 最值得告警的指标

```
notifyd_oldest_pending_age_seconds
```

它单独一条就能回答「**是不是有东西卡住了**」。队列深度正常但最老任务年龄持续上涨，
说明存在一个投不出去的目标在反复退避。**告警应该建在它上面，而不是队列深度上。**

## 八、测试与验证

```bash
make check       # gofmt + go vet + 脱敏检查 + 全部测试
make test-race   # 竞态检测（会用 -race 重新构建被测二进制）
```

### 8.1 验收标准 A1-A10（全部实现并通过）

> 它们启动**真实的 notifyd 进程**并发起真实 HTTP 请求 ——
> 因为要验证的正是「进程被 `kill -9` 之后会怎样」这类单元测试够不到的性质。
> 选自研存储时接受的「正确性需自证」这笔债，在这里还。

| # | 场景 | 断言 |
|:-:|---|---|
| **A1** | 返回 `202` 后立即 `kill -9` | 重启后任务仍在，最终被投递 |
| A2 | 目标持续 `503` | 重试间隔呈增长趋势；达上限后进死信 |
| A3 | 目标返回 `400` | **一次**尝试后进死信，1.5s 内确认无偷偷重试 |
| A4 | 同幂等键并发提交 100 次 | 只产生 1 个任务，99 次返回 `duplicate` |
| A5 | 回环 / metadata / 私网 / IPv6 / **IPv4-mapped** / CGNAT | 全部 `blocked_target` |
| A6 | 签名篡改 / 未知 key / 时间戳 ±10min / 缺签名头 | 全部 `401` |
| A7 | 一个 host 挂起 3s | 其他 host 的投递不受影响 |
| A8 | 60 个任务同时失败 | 重试时刻跨度 **3862ms，分布在 9 个分桶**（实测） |
| A9 | 576 次重试 + 压缩 | journal 仅 **13271 字节**（实测）；重启后状态一致 |
| A10 | 队列达上限 | 新提交 `429`，已有任务不受影响 |

A8 / A9 的数字是测试自己打出来的**实测值**，不是文档里的估算。

### 8.2 补充用例

| 用例 | 验证什么 |
|---|---|
| `TestA6b_SignatureCoversBody` | 用原始 body 的签名发送**目标 URL 被换成攻击者地址**的 body → `401` |
| `TestStableNotifyID` | 同一任务所有重试的 `X-Notify-Id` 恒定、`X-Notify-Attempt` 递增 |
| `TestE2E_DeadLetterSurvivesKill9` | 死信**落盘**：`kill -9` 后仍在，重投后供应商收到原封不动的 body 与自定义 header |
| `TestE2E_DeadLetterSurvivesCompactionAndKill9` | 死信经过**压缩**再崩溃，仍能重建完整请求 |
| `TestE2E_CompactionDropsSucceededCredentials` | **直接读 journal 文件**：成功任务凭据必须消失、死信的必须保留 |
| `TestE2E_SuccessResponseIsQueryable` | `200` 包裹业务错误时，响应摘要可查且活过重启 |
| `TestExampleClientScript` | 文档里的签名示例脚本真的能跑通 |

### 8.3 关于 `-race`

验收测试启动的是**独立进程**，只给测试二进制开 `-race` 检测不到 notifyd 内部的并发
（32 worker + 共享队列 + 后台刷盘）。因此用 `//go:build race` 让 race 模式下
给被测二进制也加上 `-race`。

> **一个跑了 `-race` 却没覆盖主体代码的测试，给的是虚假的安全感** ——
> 比不跑更危险，因为它会让人停止怀疑。

### 8.4 没有验证的（诚实清单）

| 没验证 | 说明 |
|---|---|
| **性能 / 吞吐** | 一个压测都没做。「千级 QPS 够用」「单锁不会成为瓶颈」**全是估算** |
| **机器掉电** | 只验证到进程级（`kill -9`）。真掉电需断电或 fault injection |
| **fsync 失败后的行为** | Linux 上 EIO 会被清除，重试可能假成功。代码方向正确但无故障注入测试 |
| **长时间运行** | 未观测 goroutine 泄漏与内存增长 |
| **压缩过程中崩溃** | 测了失败路径，没测「正好在 `rename` 那一刻被 kill」 |
| **真实第三方供应商** | mock 是按剧本行动的 |
