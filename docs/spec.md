## 0. 一句话定义

**notifyd 是一个把「调用外部 HTTP API」这件事从业务主链路上摘下来的中继服务。**

业务系统提交一个**已经构造完整**的 HTTP 请求描述，notifyd 持久化后立即返回；
此后由 notifyd 负责反复投递，直到成功或放弃。业务系统不等待、不关心响应、不重试。

一句话的反面同样重要：**notifyd 不理解任何一家供应商的业务语义**。
它是一根字节忠实的管道，不是一个集成平台。

## 1. 问题理解

### 1.1 业务方真正的痛点是什么

需求描述里有三个例子（广告回传 / CRM 状态变更 / 库存变更），表面看是「要调三个 API」，
但它们共享同一个结构性问题：

> **一次关键业务事件的提交成功，被绑定在了一个不受控的第三方的可用性上。**

不做任何处理时，业务代码会长成这样：注册成功 → 同步调广告商 API → 超时 5s →
用户注册接口 RT 飙到 5s，或者干脆失败回滚。这是把别人的 SLA 写进了自己的 SLA。

而业务方「不关心返回值」这句话，是整个设计最关键的输入 —— 它意味着：

- 投递可以**完全异步**，不需要回调、不需要结果队列、不需要响应体透传；
- 系统的成功标准是**送达**，不是「送达并正确处理」；后者是供应商的责任。

### 1.2 因此系统的核心承诺只有两条

| # | 承诺 | 含义 |
|---|---|---|
| **C1** | **收下就不丢** | 一旦返回 `202`，任务已落盘 fsync。进程 kill -9、机器掉电，重启后任务仍在。 |
| **C2** | **不放弃得太早** | 外部系统抖动（分钟级）到短期宕机（小时级）都由 notifyd 吸收，业务方无感。 |

**C1 是硬承诺，任何性能优化都不能以牺牲它为代价。**
C2 是尽力而为，有明确的放弃条件（见 §6.4），放弃时留下可人工干预的死信。

### 1.3 一个必须说清楚的边界：可靠 ≠ 精确一次

「稳定、可靠地送达」在分布式语境下只能落到 **at-least-once**。
原因见 §5.1。把「不重复」的责任错误地放在本系统，是这类系统最常见的设计事故。

## 2. 系统边界

### 2.1 本系统解决的问题

1. **异步解耦**：业务主链路不再同步等待第三方。
2. **持久化排队**：任务落盘，进程重启/崩溃不丢。
3. **重试与退避**：指数退避 + full jitter，自动吸收对端抖动与短期不可用。
4. **失败分类**：区分「重试有意义」和「重试只是浪费」，后者立即终止（见 §6.2）。
5. **入口幂等**：同一 `idempotency_key` 重复提交只产生一个任务。
6. **鉴权与完整性**：对称密钥签名，防止请求被篡改（尤其是被篡改**目标地址**）。
7. **SSRF 防护**：阻止用本服务作为跳板访问内网（见 §4.4）。
8. **死信与人工干预**：放弃的任务不消失，可查询、可手工重投。
9. **可观测**：任务状态可查、投递指标可采集。

### 2.2 本系统明确**不**解决的问题

这一节比上一节重要。每条都写明「为什么不做」和「谁来做」。

| # | 不做 | 理由 | 由谁负责 |
|---|---|---|---|
| **B1** | **精确一次投递（exactly-once）** | 跨越一个我们不控制的 HTTP 边界，网络超时时**根本无法区分**「对方没收到」和「对方收到了但响应丢了」。任何号称 exactly-once 的实现，要么依赖对端配合，要么在撒谎。 | 供应商侧按幂等键去重；notifyd 提供稳定的 `X-Notify-Id` 协助（§5.2） |
| **B2** | **投递顺序保证** | 有重试就必然有乱序：任务 A 失败退避 30 分钟，其间任务 B 成功。要保序就必须串行 + 队头阻塞，一个慢任务卡死整条队列。而三个业务场景**没有一个**需要顺序。 | 若未来真的出现有序需求，由业务方合并成单次通知，或走 §12 的分区演进 |
| **B3** | **响应内容处理 / 回调业务方** | 需求原文：业务系统不关心返回值。响应体只做**截断日志**（前 512 字节）用于排障，不解析、不存储、不回传。 | —— |
| **B4** | **供应商协议适配**（鉴权换 token、签名算法、payload 模板、字段映射） | 这是**无界**的：每接一家供应商就要改一次 notifyd，最终长成一个谁也不敢动的适配器地狱。而且只有业务系统才知道该往 CRM 传什么状态。 | 业务系统构造完整请求后提交 |
| **B5** | **多实例 HA / 水平扩展** | v1 是单进程 + 本地日志。单写者的正确性容易自证；引入多实例就要处理任务抢占、重复投递、脑裂 —— 这是这类系统绝大多数事故的来源。当前需求量级不需要。 | 见 §12 演进路线 Stage 2 |
| **B6** | **定时/延时通知、优先级队列、按供应商限速** | 需求中不存在。加进来会让调度器从「一个最小堆」变成「多队列 + 令牌桶 + 优先级抢占」。 | 有需求时再加，见 §12 |
| **B7** | **多租户配额与隔离** | 调用方是内部系统，处于同一信任域。v1 用「一个业务系统一个 key」做审计归属，不做配额。 | 内网信任边界 |
| **B8** | **超过保留期的幂等去重** | 幂等去重表常驻内存，不能无限增长。去重窗口 = 终态保留期（默认 7 天）。7 天后同 key 重投会被当作新任务。 | 已知限制，写入 API 文档 |
| **B9** | **传输内容的静态加密 / KMS** | 任务体本来就要明文发给第三方，磁盘加密属于基础设施层职责（全盘加密 / 文件系统权限）。在应用层再加一层是安全剧场。 | 运维层 |
| **B10** | **死信管理 Web UI** | 一个 HTTP 接口 + curl 足够覆盖 v1 的运维需求。 | 见 §12 |

## 4. 对外接口

### 4.1 鉴权：对称密钥签名

每个调用方分配一组 `(key_id, secret)`。请求头：

```
X-Notify-Key-Id:     crm-service
X-Notify-Timestamp:  1758000000              # Unix 秒
X-Notify-Signature:  <hex(HMAC-SHA256)>
```

签名串（`\n` 分隔，固定顺序）：

```
v1
POST
/v1/notifications
1758000000
<hex(SHA256(raw_request_body))>
```

服务端校验：

1. `key_id` 存在 → 否则 401；
2. `|now - timestamp| <= 300s` → 否则 401（限定重放窗口）；
3. `hmac.Equal` 常数时间比对 → 否则 401。

**为什么签名要覆盖 body 的哈希，而不只是签个时间戳：**
本服务的请求体里装着**目标 URL**。若只签时间戳，任何能改写请求体的中间人都能把一条
「通知 CRM」的任务改成「把用户数据 POST 到攻击者服务器」。签 body 哈希把完整性和
鉴权绑在一起，这不是可选项。

**为什么不加 nonce 缓存：** 见 §5.2 —— `idempotency_key` 强制必填后，重放同一请求在
应用层天然是 no-op（返回已存在的任务）。再维护一份带淘汰策略的 nonce 表是重复建设。
时间戳窗口负责把重放限制在 5 分钟内，幂等键负责让重放无害，两者已经闭合。

**密钥来源：** `NOTIFY_KEYS_FILE` 指向一个 `key_id:secret` 每行一条的文件（0600）。
不走环境变量 —— 环境变量会出现在 `ps`、崩溃转储和容器 inspect 里。

### 4.2 `POST /v1/notifications` —— 提交通知

```jsonc
{
  "idempotency_key": "order-98765-paid",      // 必填，<=128B，调用方保证唯一
  "target": {
    "url": "https://vendor.example.com/hook", // 必填，仅 http/https
    "method": "POST",                          // 默认 POST
    "headers": {                               // 原样透传
      "Content-Type": "application/json",
      "Authorization": "Bearer <vendor-token>"
    },
    "body": "{\"contact_id\":123,\"status\":\"paid\"}",
    "body_encoding": "utf8"                    // utf8 | base64，默认 utf8
  },
  "policy": {                                  // 全部可选
    "timeout_ms": 5000,                        // 单次尝试超时
    "max_attempts": 24,
    "deadline_ms": 86400000                    // 绝对放弃时刻（自创建起）
  }
}
```

**`body` 为什么是字符串而不是 JSON 对象：**
如果接收对象再由 notifyd 序列化，字段顺序和空白会改变 —— 而不少供应商会对
**原始 payload 字节**做签名校验。notifyd 一旦重新序列化，签名必然失效，且这个 bug
只会在特定供应商上出现，极难定位。所以 body 是**不透明字节**，进来什么样出去什么样。
这是「字节忠实管道」这一定位的具体落地。

**响应**

| 情形 | 状态码 | 体 |
|---|---|---|
| 新任务已落盘 | `202 Accepted` | `{"id":"...","state":"pending","duplicate":false}` |
| 幂等键命中已有任务 | `200 OK` | `{"id":"...","state":"succeeded","duplicate":true}` |
| 参数非法 / URL 不合法 / 目标为内网地址 | `400` | `{"error":"...","code":"invalid_target"}` |
| 签名失败 / 时间戳超窗 | `401` | —— |
| 队列积压超上限 | `429` + `Retry-After` | `{"error":"queue_full"}` |

**`202` 的语义是硬的：返回前 journal 已 fsync。** 这是承诺 C1 的唯一交付点。

### 4.3 其余接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/v1/notifications/{id}` | 查任务当前状态 + 最近 N 次尝试记录（排障用，**不供业务逻辑依赖**） |
| `GET` | `/v1/notifications?state=dead&limit=100` | 死信列表 |
| `POST` | `/v1/notifications/{id}/retry` | 手工复活死信：重置尝试计数，立即入队 |
| `GET` | `/healthz` | 存活探针（不含依赖检查，本服务无外部依赖） |
| `GET` | `/metrics` | Prometheus 文本格式（手写，见 §9） |

`/retry` 是「供应商宕机 3 天」这个场景的运维出口。没有它，死信就只是一座坟场。

### 4.4 SSRF 防护

调用方能指定任意 URL，而请求由**部署在内网的 notifyd** 发出 —— 这是典型的 confused
deputy。即便调用方都是可信内部系统，一个业务侧的注入 bug 也会把 notifyd 变成内网探针。

措施：在 `net.Dialer.Control` 钩子里，对**实际解析出的目标 IP**做检查，命中即拒绝：

```
127.0.0.0/8   ::1          回环
10/8  172.16/12  192.168/16  fd00::/8    私网
169.254/16   fe80::/10      链路本地（含云 metadata 169.254.169.254）
0.0.0.0/8    ::             通配
```

**为什么钩在 Dial 层而不是提交时校验 URL：** 提交时做 DNS 解析再放行，存在 DNS rebinding
的 TOCTOU 窗口 —— 第一次解析返回公网 IP 通过校验，实际连接时解析到 `169.254.169.254`。
`Dialer.Control` 在**建立连接前拿到最终 IP**，没有这个窗口。零依赖、约 20 行。

允许通过 `NOTIFY_ALLOW_PRIVATE_HOSTS` 显式放行（本地联调、内部 mock 用）。

## 5. 投递语义与幂等

### 5.1 语义：at-least-once

**选择 at-least-once，并把「可能重复」作为对外的显式契约写进 API 文档。**

不选 at-most-once：会丢通知，与承诺 C1 直接冲突。
不选 exactly-once：做不到。当一次 POST 超时，notifyd 有两种可能的世界状态：

- 请求没到达对端 → 不重试就丢了；
- 请求到达并被处理，只是响应在回程丢了 → 重试就重复了。

**这两种状态在 notifyd 这一侧无法区分**，没有任何本地机制能消除这个歧义。
唯一的出路是让对端去重，而对端是否去重不由我们决定。因此诚实的做法是：
选 at-least-once，把重复的可能性明确暴露给调用方和供应商，而不是假装它不存在。

### 5.2 两种幂等，责任在不同的人

这是最容易被混淆的一对概念，分开说：

| | 入口幂等（去重**提交**） | 出口幂等（去重**投递**） |
|---|---|---|
| 问题 | 业务系统重试提交，产生多个任务 | notifyd 重试投递，供应商收到多次 |
| 谁负责 | **notifyd 负责**，强保证 | **供应商负责**，notifyd 只能协助 |
| 机制 | `idempotency_key` 必填；内存索引 `key → task_id`，命中直接返回已有任务 | 每次投递携带**恒定不变**的 `X-Notify-Id: <task_id>` 和 `X-Notify-Attempt: <n>` |
| 边界 | 去重窗口 = 终态保留期（默认 7 天），见 B8 | 供应商若不按 `X-Notify-Id` 去重，重复就会发生。这是 §2.2 B1。 |

**`X-Notify-Id` 在同一任务的所有重试中保持不变**，`X-Notify-Attempt` 递增。
前者让支持幂等的供应商能去重，后者让供应商的日志能看出这是第几次 —— 这是 notifyd
在出口侧能做的全部，也应该是全部。

### 5.3 崩溃恢复时的语义体现

进程崩溃时处于 `sending` 状态的任务，**无法知道请求是否已送达**。
重启后的处理是：**重新投递**。这就是 at-least-once 在恢复路径上的直接体现 ——
我们选择「可能重复」而不是「可能丢失」，因为 C1 优先级更高。

## 6. 调度与重试

### 6.1 退避算法：指数退避 + full jitter

```
base = 1s,  cap = 1h,  max_attempts = 24

窗口   window_n = min(cap, base * 2^(n-1))
实际   delay_n  = random_uniform(0, window_n)        ← full jitter
```

**参数是算出来的，不是拍的。** 承诺 C2 要求吸收「小时级宕机」，反推重试上限：

| max_attempts | 最坏覆盖时长 | 期望覆盖时长（full jitter） |
|---|---|---|
| 12 | 0.6h | 0.3h |
| 16 | 4.1h | 2.1h |
| **24** | **12.1h** | **6.1h** |
| 30 | 18.1h | 9.1h |

初稿写的 `max_attempts=12` 只能覆盖**期望 18 分钟**的宕机，且在该次数下
`cap=1h` 根本不会被触发（第 12 次的窗口才 2048s）—— 参数与 C2 的承诺互相矛盾。
改为 24：`cap` 从第 13 次起真正生效，覆盖范围与「小时级」对得上。

**为什么是 full jitter 而不是「固定指数 + 小随机扰动」：**
考虑供应商宕机 10 分钟，期间积压 5000 个任务。若退避是确定性的，这 5000 个任务的
重试时刻高度聚集 —— 对端刚恢复就被同一秒内的 5000 个请求再次打垮，形成
「恢复 → 再次崩溃 → 再积压」的循环。full jitter 把重试时刻**均匀铺开**到整个退避窗口，
是这三种做法（无 jitter / 等量 jitter / full jitter）里对端压力峰值最低的一种。
代价是单个任务的期望延迟变为窗口的一半，对本场景完全可接受 —— 我们优化的是
**对端的存活概率**，不是单条通知的 P50。

### 6.2 失败分类：重试前先问「重试有意义吗」

盲目重试所有失败是新手实现最常见的问题：它会对着一个永远返回 `400` 的请求重试 24 次，
既浪费自己的配额，也可能触发对端的风控。

| 对端结果 | 判定 | 动作 |
|---|---|---|
| `2xx` | 成功 | → `succeeded` |
| `408` `429` | 可重试 | 退避；`429` 若带合法 `Retry-After` 则优先采用（封顶 1h） |
| `5xx` | 可重试 | 退避 |
| **其余 `4xx`**（400/401/403/404/409/422…） | **永久失败** | **不重试**，直接 → `dead`，原因 `permanent_4xx` |
| `3xx` | **永久失败** | 不跟随重定向，见下 |
| 连接被拒 / DNS 失败 / TLS 握手失败 / 超时 | 可重试 | 退避 |
| 目标 IP 命中 SSRF 黑名单 | 永久失败 | → `dead`，原因 `blocked_target` |
| 任务描述不可投递（`body_encoding` 非法等） | 永久失败 | → `dead`，原因 `bad_request_spec` |

**为什么 `401/403` 归为永久失败：** 凭据错误重试 24 次也不会变对，只会在对端留下一串
认证失败记录，可能触发账号锁定。正确的处理是立即进死信 + 告警，让人去换凭据。

**为什么不跟随 3xx 重定向：** Go 的 `http.Client` 默认跟随。对一个从内网发出请求的中继
服务，跟随重定向意味着 §4.4 的 SSRF 校验可以被绕过 —— 校验通过的公网地址返回一个
指向 `169.254.169.254` 的 `302`。因此设 `CheckRedirect` 直接返回错误，把 3xx 作为
永久失败暴露给调用方去修 URL。这是「安全性优先于便利性」的一次明确取舍。

### 6.3 并发与隔离

- 固定 worker 池（默认 32），从到期最小堆取任务。
- **per-host 并发上限**（默认 8）：`map[host]chan struct{}` 信号量。

**为什么必须有 per-host 上限：** 没有它，一个响应时间 30s 的供应商会把 32 个 worker
全部占住，其余所有供应商的通知一起饿死。这是这类系统最典型的生产事故，
而修复成本只有约 20 行。这不是过度设计，是必需的故障隔离。

**为什么不做熔断器（circuit breaker）：** 见 `decisions.md` D-010。简言之：
「退避 + per-host 上限」已经覆盖了熔断器 80% 的收益，而熔断器带来一个三态机
（closed/open/half-open）、探测策略和一组难调的阈值。v1 不值这个复杂度。

### 6.4 放弃条件与死信

满足**任一**条件即终止并进入 `dead`：

1. `attempts >= max_attempts`（默认 24，约覆盖 12.1h）；
2. `now >= created_at + deadline_ms`（默认 24h）—— 绝对时间兜底；
3. 判定为永久失败（§6.2）。

**为什么两个条件并存（诚实版）：** 在默认参数下，**先到的一定是次数上限**（12.1h < 24h），
deadline 并不在正常路径上生效。它的价值是**防御性**的，有两层：

- `policy` 允许调用方覆盖 `max_attempts` / 超时。deadline 保证无论调用方怎么调，
  一条通知的滞留时间都有一个**与退避参数无关**的上界。
- 它让「这条通知最迟什么时候我能确定它失败了」有一个可以写进对账逻辑的确定答案。
  对广告回传这类有时效性的通知，迟到的送达和没送达没有区别，**可预期的放弃时刻**
  比「尽力重试」更有用。

把它写成「两个都在正常路径上生效」是不诚实的 —— 它是兜底，不是主控。

死信**不删除**，保留至 §8 的保留期结束，可查询、可 `/retry`。

### 6.5 状态机

```
                  ┌─────────┐
   POST ─fsync──► │ pending │
                  └────┬────┘
                       │ 到期出队
                  ┌────▼────┐
        ┌─────────│ sending │─────────┐
        │ 2xx     └────┬────┘   永久失败/超限
        │              │ 可重试失败      │
   ┌────▼──────┐  ┌────▼────┐     ┌────▼───┐
   │ succeeded │  │ waiting │     │  dead  │
   └───────────┘  └────┬────┘     └────┬───┘
                       │ 退避到期        │ POST /retry
                       └────► pending ◄─┘
```

崩溃时停留在 `sending` 的任务，重放后回到 `pending`（§5.3）。

## 7. 持久化：手写 WAL

这是全项目技术难度最高的部分，也是「零第三方依赖」这条约束最贵的地方。设计目标：
**用尽可能少的机制，换到 C1 那一条硬承诺。**

### 7.1 文件格式

单个 append-only 文件 `data/journal.log`，每行一条 JSON 记录（JSONL）。四种记录：

```jsonc
{"t":"enq","id":"01J...","ts":1758000000123,"task":{ ...完整任务... }}
{"t":"att","id":"01J...","ts":1758000001456,"n":3,"res":"retry","code":503,"next":1758000061000}
{"t":"ok" ,"id":"01J...","ts":1758000002789,"n":4,"code":200}
{"t":"dead","id":"01J...","ts":1758000003000,"n":24,"why":"max_attempts"}
```

选 JSONL 而不是自定义二进制格式：可以用 `tail`/`grep`/`jq` 直接排障，
出事故时这个能力比省下来的几个字节值钱得多。

### 7.2 **fsync 策略：非对称，这是本设计的核心**

```
enq  记录  →  write + fsync，然后才返回 202     ← 阻塞
att  记录  →  write，不 fsync
ok   记录  →  write，不 fsync
dead 记录  →  write，不 fsync
                后台每 200ms 统一 fsync 一次
```

**推导过程：** 对每种记录分别问「丢了会怎样」。

| 记录 | 丢失后果 | 违反 C1？ | 结论 |
|---|---|---|---|
| `enq` | **任务彻底消失**，业务方以为发了，实际没发，且无人知晓 | **是** | 必须 fsync |
| `att` | 重放后 attempt 计数偏小 → 多重试几次 | 否 | 免 fsync |
| `ok`  | 重放后已成功的任务被重投一次 | 否（at-least-once 允许） | 免 fsync |
| `dead`| 重放后死信回到队列，再走一遍失败流程 | 否 | 免 fsync |

关键洞察：**除了 `enq`，其余记录的丢失后果都被 at-least-once 语义本身吸收了。**
而 `ok` 是数量上最多的记录（每个成功任务一条），对它 fsync 会让吞吐掉一个数量级，
却换不到任何正确性。这个非对称性不是抠性能，是**把持久化成本精确花在唯一需要它的地方**。

代价要写清楚：进程崩溃时，最近 200ms 内成功投递的任务可能被重投一次。
这是我们**主动选择**的重复，落在 at-least-once 的契约内。

### 7.3 启动重放与截断修复

```
1. 逐行读取 journal.log，维护 last_good_offset
2. 某行 JSON 解析失败 → 判定为崩溃时的半截写入
   → ftruncate 到 last_good_offset，WARN 日志，继续启动
3. 按记录类型重建内存状态：
   enq  → 新建任务，state=pending
   att  → 更新 attempt 数与 next_at，state=waiting
   ok   → state=succeeded（转为墓碑）
   dead → state=dead
4. 重放结束后，所有 pending/waiting/sending 的任务按 next_at 入最小堆
   （sending 视为 pending，见 §5.3）
```

**能处理什么：** 崩溃导致的**尾部截断**（最后一条记录写了一半）。这是
append-only + 单写者模式下唯一可能的损坏形态，由 JSON 解析失败可靠检出。

**不处理什么：** 文件中间的位翻转 / 静默损坏。防它需要给每条记录加 CRC 并处理
「中间坏了但后面是好的」的复杂分支。**明确不做** —— 磁盘完整性是文件系统和硬件的职责，
在应用层做一层弱校验属于职责错配。写入 §11 的已知限制。

### 7.4 压缩（compaction）

触发条件（同时满足）：`文件 > 64MB` **且** `冗余记录占比 > 50%`。

> **实现阶段的修正。** 初稿写的是「终态记录占比 > 50%」，写验收测试 A9 时发现这
> **量错了东西**：压缩的收益来自折叠同一任务的多条 `att` 记录（重试 100 次 =
> 100 条 `att`，压缩后只剩 1 条），而这类记录对「终态占比」的贡献是 **0**。
> 结果就是一个 99% 都是冗余重试记录的 journal 永远不会被压缩 —— 恰好漏掉了
> 最该压缩的那种情况。
>
> 正确的量法是直接比较「快照需要多少条记录」（≈ 任务数 × 2）与「磁盘上实际
> 有多少条」。这个比值就是压缩收益本身，不需要任何间接推断。

```
1. 持写锁（阻塞新的 enq，毫秒 ~ 数百毫秒级）
2. 写 journal.log.new：活跃任务的 enq 快照 + 保留期内终态任务的墓碑记录
3. fsync(journal.log.new)
4. rename(journal.log.new, journal.log)     ← 同文件系统内原子
5. fsync(dir)                                ← 保证 rename 本身落盘
6. 释放写锁
```

**为什么用「写新文件 + rename」而不是原地重写：** rename 在同一文件系统内是原子的，
任何时刻崩溃，剩下的要么是完整的旧文件、要么是完整的新文件，不存在半新半旧的中间态。
原地重写做不到这一点。`fsync(dir)` 这一步容易被漏掉 —— 没有它，rename 元数据可能还在
页缓存里，掉电后文件名指向会丢。

**已知限制：** 压缩期间阻塞写入。v1 接受（预期百毫秒级）。改成无阻塞需要双写新旧文件，
复杂度翻倍，收益在当前量级下不存在。

#### 7.4.1 终态任务的「瘦墓碑」

压缩时，**成功**任务只保留一个瘦墓碑：丢掉 `Headers` 与 `Body`，保留 `URL` 与 `Method`。

这不只是省体积（虽然省得很多）。`Headers` 里装着**供应商的 `Authorization` 凭据** ——
一个已经投递成功的任务，没有任何理由把别人的 token 在磁盘上再留 7 天。压缩顺带
把这个暴露面清掉。保留 URL 与 Method 是因为它们不敏感，而排障时「这条通知发去了
哪」是最常被问到的问题。

**死信任务必须保留完整 `Target`** —— 否则 `POST /{id}/retry` 无从重建请求。
代价是死信会在磁盘上持有供应商凭据直到过保留期，已列入 §11。

### 7.5 内存结构

| 结构 | 类型 | 用途 |
|---|---|---|
| `tasks` | `map[TaskID]*Task` | 全量任务（含保留期内终态） |
| `idem` | `map[string]TaskID` | 幂等键 → 任务，入口去重 |
| `due` | `container/heap` 最小堆，key = `next_at` | 到期调度 |
| `hostSem` | `map[string]chan struct{}` | per-host 并发信号量 |

全部由一把 `sync.RWMutex` 保护。**为什么用一把大锁而不做细粒度拆分：** v1 的目标吞吐
是千级 QPS，单锁的临界区都是纯内存 map 操作（微秒级），不会成为瓶颈。细粒度锁会引入
锁序问题和死锁风险，换来现阶段用不上的并发度。这是有意识的「先简单，量化后再优化」。

### 7.6 容量与背压

- 活跃任务数上限（默认 100,000）；超过后 `POST` 返回 `429` + `Retry-After: 5`。
- **为什么要有上限：** 若下游全线不可用且业务持续提交，无上限会一路吃满内存和磁盘，
  最终 OOM —— 那时连已收下的任务一起丢，直接违反 C1。**早拒绝，好过晚崩溃。**
  拒绝时业务方拿到明确的 `429`，可以自己决定降级策略；OOM 时业务方什么也拿不到。

## 8. 保留与清理

- 终态任务（`succeeded` / `dead`）在内存保留 **7 天**（`NOTIFY_RETENTION_DAYS`）。
- 保留期内可查状态、可 `/retry`、参与幂等去重。
- 过期后从内存移除；journal 中的记录在下次 compaction 时被丢弃。
- **副作用（B8）：幂等去重窗口 = 保留期。** 超过 7 天的同 key 重投会被当作新任务。
  这个限制必须写进 API 文档，而不是留给调用方去踩。

## 9. 可观测性

`GET /metrics`，**手写 Prometheus 文本格式**（约 30 行，零依赖）：

```
notifyd_tasks_total{state="pending|waiting|sending|succeeded|dead"}   gauge
notifyd_submitted_total{result="accepted|duplicate|rejected"}         counter
notifyd_attempts_total{outcome="success|retryable|permanent"}         counter
notifyd_attempt_duration_seconds_bucket{le="..."}                     histogram
notifyd_queue_depth                                                    gauge
notifyd_journal_bytes                                                  gauge
notifyd_oldest_pending_age_seconds                                     gauge
```

**`notifyd_oldest_pending_age_seconds` 是最重要的一个指标** —— 它单独一条就能回答
「是不是有东西卡住了」。队列深度正常但最老任务年龄持续上涨，说明存在一个投不出去的
目标在反复退避。告警应该建在它上面，而不是建在队列深度上。

结构化日志（JSON 行）写 stdout，交给宿主机的日志采集。不引入日志库。

## 10. 配置与运维

全部通过环境变量（零依赖，不引入配置解析库）。时长类一律用 Go duration 字面量
（`5s` / `1h` / `200ms`）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `NOTIFY_ADDR` | `:8080` | 监听地址 |
| `NOTIFY_DATA_DIR` | `./data` | journal 目录 |
| `NOTIFY_KEYS_FILE` | `./keys` | `key_id:secret` 每行一条，**权限必须 0600，否则拒绝启动** |
| `NOTIFY_WORKERS` | `32` | worker 池大小 |
| `NOTIFY_HOST_CONCURRENCY` | `8` | 单目标主机并发上限 |
| `NOTIFY_QUEUE_MAX` | `100000` | 活跃任务上限，超过返回 429 |
| `NOTIFY_MAX_ATTEMPTS` | `24` | 默认重试上限（约覆盖 12.1h 宕机，见 §6.1） |
| `NOTIFY_BACKOFF_BASE` | `1s` | 退避基数 |
| `NOTIFY_BACKOFF_CAP` | `1h` | 退避窗口封顶 |
| `NOTIFY_TIMEOUT` | `5s` | 默认单次投递超时 |
| `NOTIFY_DEADLINE` | `24h` | 默认绝对放弃时限 |
| `NOTIFY_DIAL_TIMEOUT` | `5s` | 建连超时 |
| `NOTIFY_RETENTION` | `168h` | 终态保留期 = 幂等窗口 |
| `NOTIFY_MAINTAIN_INTERVAL` | `1m` | 清理 + 压缩检查周期 |
| `NOTIFY_SKEW_TOLERANCE` | `5m` | 签名时间戳容忍窗口 |
| `NOTIFY_SHUTDOWN_GRACE` | `30s` | 退出宽限期 |
| `NOTIFY_COMPACT_MIN_BYTES` | `67108864` | 触发压缩的最小文件体积 |
| `NOTIFY_COMPACT_LIVE_RATIO` | `0.5` | 冗余阈值：快照所需记录数 / 实际记录数低于它才压缩 |
| `NOTIFY_ALLOW_PRIVATE_HOSTS` | `false` | 关闭 SSRF 防护（**仅联调**，同时作用于提交预检与 Dial 层） |

**优雅退出（SIGTERM）：**

```
1. HTTP 监听停止接收新请求（已建立连接正常处理完）
2. 停止从堆中取新任务
3. 等待在途投递结束，最长 grace = 30s
4. 超时未结束的在途任务：不管，重启后按 sending→pending 重放（§5.3）
5. fsync journal，关闭文件，退出
```

## 11. 已知限制（自曝清单）

不藏在文档角落，集中列出：

1. **单点。** 进程或机器宕机期间无法接收新通知（已接收的不丢）。→ §12 Stage 2
2. **重复投递可能发生。** at-least-once 的必然结果，供应商需按 `X-Notify-Id` 去重。
3. **崩溃时最近 200ms 内成功的任务可能被重投。** §7.2 的显式取舍。
4. **不检测 journal 中段静默损坏。** 只处理尾部截断。§7.3
5. **压缩期间阻塞写入**（预期百毫秒级）。§7.4
6. **幂等窗口 = 7 天。** 超窗重投会产生新任务。§8 / B8
7. **无投递顺序保证。** B2
8. **内存与磁盘随活跃任务线性增长**，靠 `NOTIFY_QUEUE_MAX` 兜底。§7.6
9. **死信在磁盘上保留供应商凭据**直到过保留期。这是 `/retry` 能重建请求的前提，
   是一个明确的取舍而非疏忽。成功任务的凭据在压缩时即被清除。§7.4.1
10. **压缩持写锁**，期间提交被阻塞（预期百毫秒级）。§7.4

## 12. 演进路线

演进的前提是**先有触发信号**，而不是先有计划。每个阶段写明「什么信号出现时才做」。

### Stage 1（当前）单实例 + 本地 WAL
适用：日均百万级以内通知，单机可承载，可容忍分钟级维护窗口。

### Stage 2 触发信号：单点不可接受，或单机磁盘/吞吐见顶
- 把 `Store` 抽成接口（**v1 就定义好**），换成 PostgreSQL：
  `SELECT ... FOR UPDATE SKIP LOCKED` 天然提供多实例任务抢占。
- notifyd 变成无状态，起 N 个实例，前面挂 LB。
- **v1 为什么就定义 Store 接口：** 这是本项目唯一一处「为未来留的口子」。
  理由是它几乎零成本（本来就要分层），而不定义的话，文件 IO 会渗透进调度逻辑，
  到时候换存储等于重写。这是**有界的**抽象，不是可插拔插件框架。

### Stage 3 触发信号：单个供应商的故障开始影响其他供应商
- 按目标 host 分区队列，独立 worker 池；
- 加入熔断器（此时它的收益才超过复杂度）、按供应商限速。

### Stage 4 触发信号：出现顺序性需求、跨区域部署、或需要重放历史流量
- 引入 Kafka：按业务键分区获得分区内有序，消费者组做水平扩展，
  日志保留期天然支持重放。
- **此时才引入 MQ 的理由：** Stage 1-3 引入 Kafka 只是把「一个文件的复杂度」换成
  「一个集群的复杂度」，而现有需求一条也用不上分区有序、消费者组、日志重放。
  到 Stage 4，这三样全都用得上了 —— 那时它才配得上它的运维成本。

### 其他增量（按需，无固定顺序）
死信自动重放策略 / 按调用方配额 / 死信管理界面 / 通知模板与供应商适配层（若 B4 的
判断被证明是错的）。

## 13. MVP 验收标准（Definition of Done）

代码写完不等于做完。以下每条都必须有**可执行的验证脚本**：

| # | 场景 | 期望 |
|---|---|---|
| A1 | 提交任务返回 202 后立即 `kill -9`，重启 | 任务仍在队列，最终被投递 |
| A2 | 目标持续返回 `503` | 重试间隔呈指数增长且带抖动；达上限后进 `dead` |
| A3 | 目标返回 `400` | **一次**尝试后立即进 `dead`，不重试 |
| A4 | 同 `idempotency_key` 并发提交 100 次 | 只产生 1 个任务，99 次返回 `200 duplicate` |
| A5 | 目标 URL 指向 `127.0.0.1` / `169.254.169.254` | 提交或投递被拒，原因 `blocked_target` |
| A6 | 签名错误 / 时间戳偏移 10 分钟 | `401` |
| A7 | 一个目标 host 恒定挂起 30s | 其他 host 的通知投递不受影响（验证 per-host 隔离） |
| A8 | 目标宕机 5 分钟后恢复，期间积压 1000 任务 | 恢复后重试时刻分散，无瞬时尖峰（验证 full jitter） |
| A9 | 灌入 10 万任务后触发 compaction | 文件缩小，重启后状态一致，无任务丢失 |
| A10 | 队列达 `NOTIFY_QUEUE_MAX` | 新提交返回 `429`，已有任务不受影响 |

A2 / A8 需要一个**可编程的 mock 供应商**（stdlib `net/http/httptest`，零依赖），
可配置返回码、延迟、恢复时间。它是测试基础设施，不进生产二进制。

### 13.1 实现状态

A1-A10 **已全部实现并通过**，见 `test/acceptance/`。它们启动**真实的 notifyd 进程**
并对其发起真实 HTTP 请求 —— 因为要验证的正是「进程被 `kill -9` 之后会怎样」这类
单元测试够不到的性质。

补充用例（超出 A1-A10）：

| 用例 | 验证内容 |
|---|---|
| `TestA6b_SignatureCoversBody` | 用原始 body 的签名发送被篡改的 body（把目标 URL 换成攻击者地址）必须 401 |
| `TestStableNotifyID` | 同一任务的所有重试携带**恒定不变**的 `X-Notify-Id`，`X-Notify-Attempt` 递增 |
| `TestDeadLetterRetry` | 死信可查询、可手工重投，重投后能成功 |

**竞态检测：** `go test ./... -race` 时，验收测试会用 `-race` 重新构建被测二进制。
这一点容易被忽略 —— 验收测试启动的是**独立进程**，只给测试二进制开 `-race` 检测不到
notifyd 内部的并发，而那才是真正需要被检测的地方（多 worker + 共享队列 + 后台刷盘）。
