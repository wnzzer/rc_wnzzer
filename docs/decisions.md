<a id="d-001"></a>
### D-001 · 零第三方依赖，单常驻进程
**状态**：✅ 已采纳 ｜ **决策人**：作者（立项约束）

- **背景**：作业允许使用开源中间件，但要求说明「为什么用 / 不用时的替代方案」。
- **选项**：
  A. 常规做法：Web 框架 + ORM + Redis/MQ + 监控 SDK。
  B. 只用标准库，单进程单二进制。
- **决定**：B。
- **理由**：这个系统的真实复杂度不在「接请求」也不在「发请求」，而在
  **崩溃不丢 + 退避正确 + 失败分类**。引入框架不会让这三件事变简单，只会把它们藏进
  一堆配置里。反过来，零依赖强迫每一行复杂度都被显式写出来、被显式论证 ——
  这恰好是作业要考察的「识别并主动管理复杂度」。
  **放弃了什么**：开箱即用的连接池/指标/存储、更短的代码量、以及「稳定性有人背书」。
- **反悔成本**：低。分层清晰的前提下，任何一层都可以后续替换为库实现。

<a id="d-002"></a>
### D-002 · Go + 手写 WAL
**状态**：✅ 已采纳 ｜ **决策人**：作者（AI 提供选项与代价分析）

- **背景**：D-001 之后，「持久化」没有免费午餐了，必须在语言和存储机制间做联合选择。
- **选项**：

  | 方案 | 优势 | 代价 |
  |---|---|---|
  | **A. Go + 手写 append-only WAL** | 单静态二进制；最贴合「常驻后台服务」；并发原语强 | 约 200-300 行自研存储层，**正确性需自证** |
  | B. Python + 标准库 `sqlite3` | `sqlite3` 属标准库，仍算零依赖；WAL 模式的事务与崩溃安全白拿 | `http.server` 偏弱；部署要带运行时；「生产级常驻服务」说服力弱 |
  | C. Go + 纯内存队列 | 代码量最小 | **重启丢全部在途任务**，与需求原文「稳定、可靠地送达」正面冲突 |

- **决定**：A。
- **理由**：C 直接违反核心承诺 C1，出局。A vs B 是真正的权衡：B 用标准库换来了免费的
  持久化正确性，这是很强的论点；但本作业考察的恰恰是工程判断的深度，而**手写 WAL 里的
  非对称 fsync 策略（D-005）、尾部截断修复、rename 原子压缩**，正是最能体现真实工程
  经验的部分 —— 用 SQLite 会把这部分思考整个外包掉。
  **放弃了什么**：SQLite 久经考验的崩溃安全；换来的是必须用测试（验收项 A1/A9）自证正确。
- **反悔成本**：中。若自研存储层出现无法收敛的正确性问题，Go 生态可换 `modernc.org/sqlite`
  （纯 Go，无 CGO），代价是破坏 D-001。此为**明确的兜底方案**，不是失败。

<a id="d-003"></a>
### D-003 · 投递语义选 at-least-once
**状态**：✅ 已采纳（同时❌否决 exactly-once）

- **背景**：作业必答题「你选择的通知投递语义是什么」。
- **选项**：at-most-once / at-least-once / exactly-once。
- **决定**：at-least-once，并把「可能重复」写进对外 API 契约。
- **理由**：一次 POST 超时后，「对方没收到」和「对方收到了但响应丢了」这两种世界状态
  在本服务侧**不可区分**，没有任何本地机制能消除该歧义。声称 exactly-once 要么依赖
  对端配合（那就不是我们的保证），要么是在撒谎。at-most-once 会丢，违反 C1。
  **放弃了什么**：「绝不重复」这个对调用方更省心的承诺。作为补偿，每次投递携带恒定的
  `X-Notify-Id`，让愿意去重的供应商能去重。
- **反悔成本**：不适用 —— 这是物理约束，不是偏好。

<a id="d-004"></a>
### D-004 · `idempotency_key` 强制必填，并因此取消 nonce 缓存
**状态**：✅ 已采纳（含❌否决 nonce 表）

- **背景**：签名鉴权的标准做法通常是「时间戳窗口 + nonce 去重表」防重放。AI 初版方案
  给的也是这个组合。
- **决定**：保留时间戳窗口（±300s），**去掉 nonce 表**，改为强制要求 `idempotency_key`。
- **理由**：`idempotency_key` 必填后，重放一个完整请求在应用层天然是 no-op ——
  命中幂等索引，返回已存在的任务，不产生任何新副作用。此时再维护一张带淘汰策略的
  nonce 表，是用一个新的有状态组件去解决一个已经被解决的问题。
  时间戳窗口负责**限制重放窗口**，幂等键负责**让重放无害**，两者已经闭合。
  **放弃了什么**：对「不带幂等键的请求」的防重放能力 —— 但这种请求已被强制必填排除。
- **反悔成本**：低，加回 nonce 表是独立模块。

<a id="d-005"></a>
### D-005 · fsync 非对称策略（本设计的核心取舍）
**状态**：✅ 已采纳

- **背景**：WAL 有四类记录。全部 fsync 则吞吐掉一个数量级；全不 fsync 则违反 C1。
- **决定**：**只对 `enq` 记录做同步 fsync**（在返回 202 之前）；`att` / `ok` / `dead`
  只 write 不 fsync，由后台每 200ms 统一 fsync。
- **理由**：对每类记录分别问「丢了会怎样」，答案是非对称的 ——
  `enq` 丢失 = 任务彻底消失且无人知晓 = **违反 C1**；
  其余三类丢失的后果（重试次数偏小、已成功任务被重投、死信回队）**全部落在
  at-least-once 契约内**，已被 D-003 允许。而 `ok` 恰好是数量上最多的记录，
  对它 fsync 付出最大成本却换不到任何正确性。
  **放弃了什么**：崩溃时最近 200ms 内成功投递的任务可能被重投一次。
  这是**主动选择的重复**，已写入 §11 已知限制。
- **反悔成本**：极低，一行配置即可改为全量 fsync。

<a id="d-006"></a>
### D-006 · journal 用 JSONL，不用自定义二进制格式
**状态**：✅ 已采纳

- **理由**：出事故时能直接 `tail`/`grep`/`jq` 看日志内容，这个能力比省下的字节值钱得多。
  二进制格式需要配套的 dump 工具，而那个工具永远是在你最需要它的时候还没写。
  **放弃了什么**：存储空间与解析性能（压缩机制 D-已在 §7.4 覆盖体积问题）。

<a id="d-007"></a>
### D-007 · 不做 CRC / 中段静默损坏检测
**状态**：❌ 已否决 ｜ **来源**：AI 建议

- **AI 的建议**：每条 WAL 记录附加 CRC32，重放时校验，跳过损坏记录。
- **否决理由**：append-only + 单写者模式下，崩溃能造成的**唯一**损坏形态是尾部截断，
  而它已经被「JSON 解析失败 → ftruncate 到最后一个完好偏移」可靠覆盖。
  CRC 针对的是磁盘位翻转/静默损坏 —— 那是文件系统和硬件的职责（ZFS/btrfs 校验、ECC），
  在应用层加一层弱校验属于职责错配，还会引出「中间坏了但后面是好的，要不要跳过续读」
  这种没有正确答案的分支。
  **代价**：若真的发生中段损坏，重放会在该处截断，丢失其后的记录。已列入 §11 自曝清单。
- **重新引入成本**：低（记录格式加一个字段）。

<a id="d-008"></a>
### D-008 · `target.body` 作为不透明字符串透传
**状态**：✅ 已采纳

- **背景**：AI 初版把 body 设计成 JSON 对象，读起来更自然。
- **否决理由**：若由 notifyd 重新序列化，字段顺序和空白会改变，而**不少供应商对原始
  payload 字节做签名校验** —— 重序列化后签名必然失效。更糟的是，这个 bug 只在特定
  供应商上出现，排查时几乎不会往「中继服务改了我的 JSON」这个方向想。
  因此 body 是不透明字节（`body_encoding: utf8|base64`），进来什么样出去什么样。
  **放弃了什么**：API 可读性，以及服务端对 payload 做校验/改写的可能（本来也不该做，见 D-020）。

<a id="d-009"></a>
### D-009 · 非 408/429 的 4xx 判为永久失败，立即进死信
**状态**：✅ 已采纳

- **理由**：`400` 不会因为重试变成 `200`。对 `401/403` 反复重试更糟 ——
  会在对端积累一串认证失败记录，可能触发账号锁定或风控。正确处理是立即进死信 + 告警，
  让人去换凭据。**盲目重试一切失败**是这类系统最常见的实现缺陷。
  **放弃了什么**：对「供应商短暂错误地返回 4xx」这种罕见情况的自愈能力 ——
  由 `/retry` 接口人工兜底。

<a id="d-010"></a>
### D-010 · 不跟随 3xx 重定向，视为永久失败
**状态**：✅ 已采纳

- **理由**：Go 的 `http.Client` 默认跟随重定向，这会让 D-015 的 SSRF 校验被绕过 ——
  一个通过校验的公网地址返回指向 `169.254.169.254` 的 302 即可。安全性优先于便利性：
  设 `CheckRedirect` 返回错误，把 3xx 暴露给调用方去修 URL。
  **放弃了什么**：对「供应商把 http 永久重定向到 https」这类合法场景的自动适应。

<a id="d-011"></a>
### D-011 · 指数退避使用 full jitter
**状态**：✅ 已采纳

- **选项**：无 jitter / 等量 jitter（`window/2 + rand(window/2)`）/ full jitter（`rand(0, window)`）。
- **决定**：full jitter。
- **理由**：供应商宕机 10 分钟、积压 5000 任务的场景下，确定性退避会让这 5000 次重试
  聚集在同一秒 —— 对端刚恢复就被二次打垮，形成「恢复→再崩→再积压」的循环。
  full jitter 把重试时刻均匀铺开到整个窗口，三种做法中对端压力峰值最低。
  **放弃了什么**：单条通知的期望延迟翻倍（约为窗口的一半）。
  我们在这里优化的是**对端的存活概率**，不是单条通知的 P50 —— 这个优先级排序是刻意的。

<a id="d-012"></a>
### D-012 · 次数上限与绝对 deadline 双条件并存
**状态**：✅ 已采纳（参数经自查后修正）

- **初稿理由（已被推翻）**：「次数上限防无限重试，deadline 防退避窗口拉得太长导致
  三天后才放弃」。
- **自查后的修正**：把默认参数（base=1s, cap=1h, max_attempts=12）实际算了一遍 ——
  12 次尝试只覆盖**期望 18 分钟 / 最坏 36 分钟**的宕机，`cap=1h` 在该次数下**从未被触发**
  （第 12 次窗口仅 2048s），`deadline=24h` 更是永远不可能先到。
  也就是说：初稿的三个参数里有两个是**死参数**，而 §1.2 承诺 C2 写的「吸收小时级宕机」
  根本没有被参数兑现。
- **最终决定**：`max_attempts` 改为 **24**（最坏 12.1h / 期望 6.1h），`cap` 从第 13 次起
  真正生效；`deadline` 明确降级为**防御性兜底**，不再假装它在正常路径上生效 ——
  它的真实价值是「无论调用方怎么覆盖 policy，滞留时间都有一个与退避参数无关的上界」，
  以及给对账逻辑一个确定的放弃时刻。
- **这条记录本身的意义**：一个**看起来很合理、每个参数都有名字**的配置组合，
  算一遍才发现其中两个从不生效。默认值必须是算出来的，不是抄来的。

<a id="d-013"></a>
### D-013 · per-host 并发上限（故障隔离）
**状态**：✅ 已采纳

- **背景**：这条曾被自我质疑为「MVP 是否过度」。
- **理由**：没有它，一个 RT 30s 的供应商会占满全部 32 个 worker，其余所有供应商的通知
  一起饿死 —— 这是这类系统**最典型的生产事故**，而不是理论风险。
  实现成本约 20 行（`map[host]chan struct{}`）。收益与成本严重不对称，因此它不是
  过度设计，是必需的故障隔离。判断标准：「不加它，v1 会坏在哪」有明确答案。

<a id="d-014"></a>
### D-014 · 不做熔断器
**状态**：❌ 已否决 ｜ **来源**：AI 建议

- **AI 的建议**：为每个目标 host 加 closed/open/half-open 三态熔断器，连续失败 N 次后
  打开，冷却期后半开探测。
- **否决理由**：D-013（per-host 上限）+ D-011（full jitter 退避）已经覆盖了熔断器的
  主要收益 —— 前者防止资源被单个坏目标占满，后者防止恢复时的惊群。
  熔断器额外带来一个三态机、探测策略，以及一组**没有先验数据就调不对**的阈值
  （连续失败多少次？冷却多久？半开放多少流量？）。在没有真实故障数据之前，
  这些阈值只能拍脑袋，拍错了比不熔断更危险（误熔断会直接中断正常投递）。
  **代价**：对一个长期宕机的目标，仍会按退避节奏持续发出探测请求（频率很低，可接受）。
- **重新引入时机**：§12 Stage 3 —— 当「单个供应商故障开始影响其他供应商」的信号出现时。

<a id="d-015"></a>
### D-015 · SSRF 防护钩在 `net.Dialer.Control`，而非提交时校验 URL
**状态**：✅ 已采纳

- **背景**：调用方能指定任意 URL，请求由部署在内网的 notifyd 发出 —— 典型 confused deputy。
- **选项**：A. 提交时解析 URL + DNS 查询后判断 IP；B. 在 Dial 层对实际连接的 IP 判断。
- **决定**：B。
- **理由**：A 存在 DNS rebinding 的 TOCTOU 窗口 —— 校验时解析到公网 IP 放行，
  真正连接时解析到 `169.254.169.254`。`Dialer.Control` 在**建立连接前拿到最终 IP**，
  没有这个窗口。零依赖、约 20 行。
  **放弃了什么**：无法在提交时就返回明确错误（部分情况要等到首次投递才拒绝）。
  为兼顾体验，提交时仍做一次廉价的 URL 格式与字面 IP 检查，Dial 层做权威判定。

<a id="d-016"></a>
### D-016 · 内存状态用一把 `sync.RWMutex`
**状态**：✅ 已采纳（❌否决细粒度分片锁）

- **理由**：v1 目标吞吐千级 QPS，临界区全是纯内存 map 操作（微秒级），不会成为瓶颈。

### D-017 · 活跃任务数上限 + 429 背压
**状态**：✅ 已采纳

### D-018 · 不引入消息队列（Kafka / RabbitMQ / Redis Streams）
**状态**：❌ 已否决 ｜ **来源**：AI 建议（几乎是这类需求的默认答案）

- **AI 的建议**：业务系统 → Kafka → 消费者投递；重试用延迟队列/死信队列。
- **否决理由**：MQ 提供的核心能力是**分区有序、消费者组水平扩展、日志重放、跨系统解耦**。
  逐条对照本需求：不需要有序（D-027）、单实例够用（D-021）、不需要重放历史流量、
  解耦本来就是本服务自身提供的。**一条都用不上。**
  引入它等于把「一个本地文件的复杂度」换成「一个集群的复杂度」：运维、容量规划、
  版本升级、监控、以及一个新的 SPOF。
  **不使用时的替代方案**：本地 append-only WAL（§7）—— 在单机可承载的量级下，
  它提供了 MQ 在本场景中被实际使用到的全部能力。
- **重新引入时机**：§12 Stage 4 —— 出现顺序性需求、跨区域部署或流量重放需求时。
  那时上面四项能力会同时用上，MQ 才配得上它的运维成本。

### D-019 · 不引入外部数据库 + 调度框架
**状态**：❌ 已否决 ｜ **来源**：AI 建议

- **AI 的建议**：MySQL 存任务表 + Quartz / XXL-JOB 扫表调度。
- **否决理由**：为了跑一个「按时间取到期任务」的循环，要引入两套需要独立运维的基础设施。

- **重新引入时机**：§12 Stage 2，且是「Postgres + `FOR UPDATE SKIP LOCKED`」这种

### D-020 · 不做供应商适配层 / payload 模板引擎
**状态**：❌ 已否决 ｜ **来源**：AI 建议

- **AI 的建议**：内置供应商注册表，支持 OAuth token 自动刷新、各家签名算法、
  payload 字段映射模板（如 Jinja/Go template）。
- **否决理由**：这是**无界**需求 —— 每接一家供应商就要改一次 notifyd，最终长成一个
  谁也不敢动的适配器地狱，且发布节奏被最慢的那家供应商绑架。
  更根本的是：**只有业务系统知道该往 CRM 传什么状态**，适配逻辑天然属于业务侧知识。
  notifyd 定位是「字节忠实的管道」（D-008），保持无知是它的特性而非缺陷。
  **代价**：业务系统要自己构造完整请求，多写一点代码。这个成本分散在各业务方，
  且每一方只需关心自己那一家。
- **重新引入时机**：若「多个业务系统对同一供应商重复实现了同样的适配逻辑」这个信号
  出现，正确的解法也是抽一个**共享客户端库**，而不是把它塞进中继服务。

### D-021 · v1 不做多实例 HA / 分布式锁 / leader 选举
**状态**：❌ 已否决 ｜ **来源**：AI 建议

- **AI 的建议**：多实例部署，用 Redis 分布式锁或 etcd 选主避免重复投递。
- **否决理由**：单写者 append-only 日志的正确性**容易自证**（验收项 A1/A9 可覆盖）；

  **代价**：进程/机器宕机期间无法接收新通知（已接收的不丢）。已列入 §11 自曝清单。
- **重新引入时机**：§12 Stage 2，届时用 Postgres `SKIP LOCKED` 把抢占问题交给数据库，
  而不是自己实现分布式锁。

## 实现阶段产生的决策（D-032 起）

> 以下决策全部诞生于**写代码或写测试的过程中**，不是设计阶段想出来的。
> 其中 D-032、D-033、D-034 直接推翻了设计初稿的判断 —— 这类修正比一次写对更值得记录。

<a id="d-032"></a>
### D-032 · 压缩触发条件改用「冗余记录占比」
**状态**：✅ 已采纳（推翻设计初稿）｜ **发现于**：写验收测试 A9 时

- **初稿方案**：`文件 > 64MB 且 终态记录占比 > 50%` 时压缩。
- **发现的问题**：这个条件**量错了东西**。压缩的收益来自折叠同一任务的多条 `att`
  记录（一个重试 100 次的任务在 journal 里有 1 条 `enq` + 100 条 `att`，压缩后只剩
  2 条），而 `att` 记录对「终态占比」的贡献是 **0**。
  实测：25 个任务累计 500+ 次重试，终态占比只有 3.4%，**压缩永远不会触发** ——
  恰好漏掉了最该压缩的那种情况。而 journal 在持续膨胀。
- **决定**：改为比较「快照需要多少条记录」（≈ 任务数 × 2）与「磁盘上实际有多少条」，
  低于阈值即压缩。
- **理由**：这个比值**就是压缩收益本身**，不需要任何间接推断。副作用是它在
  「60 个任务各成功一次」的场景下正确地**不触发**（那里确实无事可压），
  而旧条件会在那里做无用功。
- **实测效果**：532 次重试后 journal 稳定在 17KB（不压缩会是十万字节量级）。
- **教训**：一个指标「看起来相关」不等于它度量的是你要的东西。
  设计时挑的代理指标，必须用一个能让它失效的场景验证过。

<a id="d-033"></a>
### D-033 · 成功任务压缩为「瘦墓碑」，顺带清除供应商凭据
**状态**：✅ 已采纳 ｜ **发现于**：排查 A9 压缩收益不足时

- **背景**：压缩后 journal 只从 27KB 降到 22.8KB。查下去发现压缩把已成功任务的
  **完整 `Target`**（含 `Headers` 与 `Body`）当墓碑留了下来。
- **决定**：成功任务的墓碑只保留 `ID / IdemKey / URL / Method` 与状态，丢掉
  `Headers` 与 `Body`。死信**保留完整 Target**。
- **理由**：成功任务的墓碑此后只有两个用途 —— 参与幂等去重、供状态查询，
  `Headers`/`Body` 再也不会被读到。
  而更要紧的是：**`Headers` 里装着供应商的 `Authorization` 凭据**。一个已经投递
  成功的任务，没有任何理由把别人的 token 在磁盘上再留 7 天。这本来是个体积问题，
  查下去发现它同时是个凭据留存问题。
  保留 URL 与 Method 是因为它们不敏感，而「这条通知发去了哪」是排障最常问的。
- **为什么死信不能瘦身**：`POST /{id}/retry` 需要完整请求才能重建投递。
  代价是死信会在磁盘上持有凭据直到过保留期 —— 这是一个**明确的取舍**，
  已写进 spec §11 自曝清单，而不是留着不说。

<a id="d-034"></a>
### D-034 · 提交预检与 Dial 层必须共用同一个放行开关
**状态**：✅ 已采纳（修复缺陷）｜ **发现于**：第一次跑验收测试，11 个用例集体失败

- **缺陷**：SSRF 防护有两处实现 —— 提交时的廉价预检（`ValidateTargetURL`）与
  Dial 层的权威判定（`Dialer.Control`）。`NOTIFY_ALLOW_PRIVATE_HOSTS` 只接到了
  Dial 层，预检**无条件**拒绝私网地址。结果是开关形同虚设，而症状（提交被 400 拒绝）
  指向的方向完全错误。
- **决定**：把开关透传给预检，并在两处都写明「必须取同一个值」。
- **教训**：同一条策略在两处实现时，最容易出的错不是逻辑写反，而是**其中一处漏掉了
  例外分支**。而且漏掉的通常是更宽松的那处 —— 于是开关等于没有，报错还指向别处。
  单测各自都能过，只有端到端测试能抓到。

<a id="d-035"></a>
### D-035 · 永久失败拆成三个独立哨兵错误
**状态**：✅ 已采纳 ｜ **发现于**：code review 自查

- **背景**：实现 `doRequest` 时，为了让「body 无法 base64 解码」这类错误被判为永久失败，
  我直接借用了 `ErrBlockedTarget` 去包装它 —— 反正 `Classify` 认它。
- **问题**：能跑通，但死信原因会显示成 `blocked_target`。排障的人会去查网段拦截，
  而真正的问题是 payload 编码写错了。**一个会把人引到错误方向的错误信息，
  比没有错误信息更糟。**
- **决定**：拆成 `ErrBlockedTarget` / `ErrBadRequestSpec` 两个哨兵，加上「对端返回
  3xx/4xx」这一类，死信原因对应 `blocked_target` / `bad_request_spec` /
  `permanent_response`。
- **理由**：死信原因会出现在告警和运维界面上，它的唯一价值就是**把人直接指向问题类型**。
  为了省一个 error 变量而牺牲这一点，省错了地方。

<a id="d-036"></a>
### D-036 · 本地拥塞导致的改期，不计入重试预算、也不写 WAL
**状态**：✅ 已采纳

- **背景**：per-host 并发满时，任务要放回队列稍后再试。
- **决定**：这种改期**不计入 attempts**，且**不写 WAL 记录**。
- **理由**：
  1. 不计入尝试次数 —— 本地拥塞不是对端的错，不该消耗任务有限的重试预算。
     否则一个繁忙的供应商会让任务在还没真正投递过几次时就耗尽次数进死信。
  2. 不写 WAL —— 这是纯粹的**排程**调整，不是投递结果。即便此刻崩溃，
     该任务回放后也会作为 pending 重新排程，结果完全一致。
     为它落盘等于用磁盘 IO 去持久化一个无需持久化的事实。

<a id="d-037"></a>
### D-037 · 有序退出不打断在途投递
**状态**：✅ 已采纳

- **背景**：收到 SIGTERM 时，正在飞行中的 HTTP 请求怎么办。
- **选项**：A. 取消它们的 context，立刻中断；B. 让它们自然跑完，用 grace 兜底。
- **决定**：B。投递用的 context 刻意**不继承**调度循环的 ctx。
- **理由**：一个已经发出去的请求，很可能对端已经收到并处理了。拦腰打断它
  只会把一次「大概率成功」变成一次「结果未知」，重启后必然重投 ——
  凭空制造一次不必要的重复投递。宽限期（默认 30s）已经足以让绝大多数请求
  （默认超时 5s）跑完。
- **代价**：超过宽限期仍未结束的任务重启后会被重投。落在 at-least-once 契约内。

### D-039 · `-race` 时用 `-race` 重新构建被测二进制
**状态**：✅ 已采纳 ｜ **发现于**：第一次跑 `go test -race`

- **问题**：验收测试启动的是**独立进程**。对测试二进制开 `-race`，只能检测测试脚手架
  自己（当时确实抓到了脚手架里一个 `bytes.Buffer` 的竞态），但**完全检测不到
  notifyd 内部的并发** —— 而那才是真正需要被检测的地方：32 个 worker、共享队列、
  后台刷盘协程、per-host 信号量。
- **决定**：用 `//go:build race` 条件编译的常量，让 `TestMain` 在 race 模式下
  给被测二进制也加上 `-race`。
- **理由**：一个跑了 `-race` 却没检测到主体代码的测试，给的是**虚假的安全感** ——
  比不跑更危险，因为它会让人停止怀疑。

<a id="d-041"></a>
### D-041 · 凭据清理独立成第二条压缩触发线
**状态**：✅ 已采纳（修复 D-033 的一个漏洞）｜ **发现于**：写死信 e2e 测试时

- **背景**：D-033 让压缩把成功任务瘦身，顺带清掉磁盘上的供应商 `Authorization`。
- **发现的问题**：这个安全性质**挂错了地方**。它搭在「空间收益」那条触发线上，
  于是变成**机会性的，不是保证** —— 磁盘上的字节只能靠重写 journal 抹掉，
  而一个低冗余的 journal 永远不会触发压缩，凭据就能安稳躺满整个保留期（默认 7 天）。
- **怎么发现的**：写 `TestE2E_CompactionDropsSucceededCredentials` 时，
  没有通过 API 间接推断，而是**直接读 journal 文件 grep 凭据串**。
  结果是任务成功后凭据仍在盘上，且再也等不到下一次压缩。
  用 API 查是查不出来的 —— `taskView` 本来就不返回 headers，查它什么也证明不了。
- **决定**：加一条**独立**的触发线：`unstripped >= StripThreshold`（默认 1000）时，
  即便没有任何空间收益也强制压缩一次。
- **理由**：一个安全性质如果依赖另一个**为完全不同目的而设**的条件顺带满足，
  它就不是一个性质，只是一个巧合。要么给它自己的触发条件，要么老实承认它是尽力而为。
  代价是偶尔做一次没有空间收益的压缩 —— 相对于「凭据留存时间有上界」这个收益，很便宜。
- **附带的教训（关于验证方式）**：这个漏洞只有**直接检查磁盘**才能发现。
  凡是「某某数据不应该出现在某处」这类性质，就该到那处去看，而不是从接口反推。

## 对 D-005 的一处澄清（非新决策）

写 `TestE2E_DeadLetterSurvivesKill9` 时，第一版断言写成了「重启后死信不该被重新投递」，
测试失败。查下来**不是代码的问题，是断言写错了** —— 非对称 fsync 策略里明明白白写着
`dead` 记录不同步落盘、丢失的后果是「死信回到队列，再走一遍失败流程」。

我在写测试时凭直觉认为「死信就是终态、不该再动」，忘了自己两天前做的决策。
断言改为「额外投递有界（至多一次）且必然收敛回 dead」—— 这才是真实契约。

**运维上的含义值得单独说清楚，已补进 spec §11**：看到一条死信，不等于它不会再被投递
一次。对供应商而言这是一次重复投递，落在 at-least-once 契约内；但如果有人盯着死信
列表做人工处理，需要知道这件事。
